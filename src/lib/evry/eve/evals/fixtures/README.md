# Production-bound evaluation fixtures

Run the unpaid tool-path proof from the repository root:

```sh
EVRY_EVE_FIXTURE_PROOF=1 node --import tsx --test src/lib/evry/eve/evals/fixtures/production.test.ts
```

Node 24 and Docker are required. The test creates a randomly named, loopback-only Postgres container and Neon HTTP proxy, applies the repository SQL migrations, and removes both containers, their temporary storage, and their network in `finally`. It never uses the developer's configured database. No model requests or actual emails are sent.

The proof runs the production typed registry, production domain queries, actual Neon HTTP driver, fresh database-backed session authorization, saved-location and full-template helpers. Each case receives a separate plant and deterministic record IDs. Independent SQL checks the seeded ground truth before the agent runs. Duplicate interview rows, foreign records, another assignee, completed/overdue/undated tasks, and RSVP-only attendance are distractors.

`createProductionEveEvalAdapter` accepts a `runProduction` callback to the real Eve runtime. Pass its instrumented registry to both direct tools and code mode. Forward `onPresentResult(callId)` only from the host's successful authorized `present_result` resolution. Never call it from model prose, draft state, or a model-supplied list of IDs. The callback returns prose, measured timing, actual total generation-plus-judge cost, clarification count, and an independent quality judgment. It cannot supply result facts or safety verdicts.

The adapter derives displayed IDs and totals from captured tool artifacts. Launch coverage requires successful filtered reads across launch date, open milestones, vacant roles, and upcoming meetings. Read authorization counts come from the real session authorizer. Test-only Postgres triggers count domain inserts, updates, and deletes, including changes later reversed. A fetch interceptor blocks and counts Resend attempts. These are scoped fixture checks, not a claim that all security properties have been proven.

For a compiled HTTP runtime, choose `captureMode: "isolated_http"`. The runner receives the disposable `sessionToken` (raw cookie) and `sessionId` (stored hash). It must return `hostCapture` from a private, authenticated runtime observation journal, never from SSE model text or a browser payload. The adapter checks result-reference integrity and derives facts from those captured tool outputs. Missing captures, duplicate call IDs, unknown presentation references, or costs omitted from the total fail the run. Nested preparation authorization calls may make the fresh-authorization count exceed the number of read calls; refusals still fail the gate. Actual database audit and ground truth remain independent of the HTTP runner.

For orientation, provide the real `preparation` callback and `readPreparedFacts`, which must project the persisted, server-built immutable plan. HTTP mode uses the runtime's preparation and needs only `readPreparedFacts`. The latter returns meeting type, local date/time, timezone, duration, recipient IDs, and saved location ID. It must not project model arguments or draft state. Without these bindings the orientation evaluation is **blocked**. The unpaid test separately proves its date, saved-location, saved-template, tenant isolation, and revoked-session helpers.

Seven read regressions are bound. The eighth orientation case requires those production preparation bindings. Five original questions are also bound: `tasks-08`, `roles-01`, `launch-01`, `wiki-03`, and `documents-01`. Other historical questions and regression fixtures remain blocked rather than gaining invented passing observations. The scripted drivers deliberately supply `judge: null`, so their observations fail `quality_not_reviewed`; passing tests prove data/tool instrumentation, not Luna's behavior. Run a real Eve driver and an independent judge before reporting agent quality.

Run `EVRY_EVE_HISTORICAL_PROOF=1 node --import tsx --test src/lib/evry/eve/evals/fixtures/historical.test.ts` for the five original-question fixtures. Task refinement checks all three result sets and demonstrates a failure when ownership is dropped. The original question says "tasks", not "pending tasks", so completed tasks remain eligible. Role vacancy is checked against active assignments across two ministries, with stale role status and inactive membership distractors. Each role is one seat under the database constraint; the corpus wording about multiple positions does not imply a capacity field exists. Launch checks the exact countdown and remaining milestone IDs. Wiki checks the retrieved source bodies and citation links, including plant-over-global precedence and draft/foreign exclusion. Documents checks the actual code-defined Vision Meeting template catalog and formats. `documents-04` remains blocked because its two referenced generated files and stored bytes have not been bound.

`cleanup()` revokes the case's session. Domain fixture rows remain only in the disposable suite database until stack cleanup; this respects append-only Evry plan/receipt records. Use one adapter and serial runs per suite process because the outbound interceptor is process-wide. Always restore the global fetch hook and dispose the stack in `finally`, including failures and budget exhaustion.

## Exact approval and migration proofs

`EVRY_EVE_PLAN_PROOF=1 node --import tsx --test src/lib/evry/eve/evals/fixtures/plan-api.test.ts` invokes the real preparation, review API and production executor. It intercepts the Resend HTTP boundary, simulates a temporary provider failure, and checks persisted orientation details, core-member recipients, invalidated reviews and duplicate-free retries. It does not call a model.

`migration.test.ts` proves 0079 using the versioned `pnpm db:migrate` command for baseline, application and reapplication. Set `EVRY_EVE_MIGRATION_PROOF=1`, `PG_MODULE` to an installed `pg/lib/index.js`, and optionally `PNPM_BIN` to pnpm 10. The driver is loaded into the scratch migration subprocess only, since the production Neon WebSocket driver cannot speak to ordinary Docker Postgres. No repository dependency or shared environment file is changed. The rollback drops only the new Eve session table and its exact scratch ledger entry; prior ledger rows and parent records are asserted unchanged. Verbatim command transcripts are retained in the printed temporary evidence directory.
