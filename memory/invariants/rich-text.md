# Rich Text — Stored HTML & the Sanitiser

Why and how, for the Rich Text rules in [`../invariants.md`](../invariants.md). One feature wearing two names: **COM-017** gave a message body an editor, **T-021** gave a task description the same one. They share every module below, which is the whole point — a second editor or a second sanitiser is the bug this domain exists to prevent.

**Applies to:** `src/lib/rich-text/**`, `src/components/shared/rich-text-editor.tsx`, `src/components/shared/rich-text.tsx`, `src/lib/email/components/communication-email.tsx`, `src/lib/tasks/descriptions.ts`, and every other writer or reader of a rich-text body.

**Source:** `sanitize.ts` (the sanitiser and `sanitizeUrl`), `format.ts` (the door, `richTextToPlainText`, `isRichTextEmpty`), `email-segments.ts` (the RSVP splitter), `src/lib/communication/merge.ts` (substitution), `src/lib/tasks/descriptions.ts` (the task write gate).

## The server is the gate, not the editor

- A body composed in the editor is stored as HTML, and the SERVER is what makes it safe: `sendCommunication` sanitises before the insert, because every export of the compose action is a POSTable endpoint that never saw the toolbar. The editor's paste-time pass is a courtesy, never the gate.
- ONE sanitiser, `sanitizeRichText` (`src/lib/rich-text/sanitize.ts`), allow-list only: nine elements, and `href` on `<a>` is the only attribute that survives. Never a second sanitiser, and never a regex that "strips script tags" — that is the shape of every XSS that ever shipped.

## Idempotence, and the entities that make it hard

- `sanitizeRichText` is IDEMPOTENT, and that is a correctness requirement, not a nicety: its input is HTML in which `&`, `<`, `>` and U+00A0 are ALREADY encoded by the browser's innerHTML serialisation, and one body is sanitised 2–4 times on its way to a recipient. Text nodes are therefore DECODED (`decodeTextEntities`) before they are re-escaped. Escaping raw source text is what delivered `Bob &amp; Sue &lt;3` to an inbox, a different wrong string to the text/plain half, and a third to the COM-015 preview.
- `&nbsp;` in body text becomes the U+00A0 CHARACTER, which `escapeHtml` deliberately leaves alone; re-emitting `&nbsp;` puts back the `&` the next pass would escape. `decodeHtmlEntities` still flattens it to a space for URLs — that is what lets `URL_NOISE` catch `java&nbsp;script:`. Two callers, two rules, one decoder.

## One sanitise per surface, one renderer for all of them

- A body is sanitised in exactly ONE place per surface, and there is ONE read-only renderer for every surface: `RichText` (`src/components/shared/rich-text.tsx`), which owns the sanitise AND the merge. A caller that sanitised first and let the component sanitise again is the shape that corrupted the message detail page worse than the email; a surface that hand-rolls its own `dangerouslySetInnerHTML` is the shape the task detail page shipped, a second copy of the component plus a fourth copy of the prose classes, already drifted in spacing and link colour. The prose classes have exactly TWO spellings, both in `rich-text-editor-controls.ts`: `RICH_TEXT_PROSE_CLASS` (the app's voice — the editor canvas and `RichText`) and `EMAIL_RICH_TEXT_PROSE_CLASS` (the recipient's — the COM-015 preview only, which mimics `CommunicationEmail`'s inline styles rather than this app's theme).

## URLs: vetted before substitution, so a token decides neither half of the origin

- A URL is vetted by `sanitizeUrl` AFTER entity-decoding and control-character stripping, or `javascript:` walks in spelled `&#106;avascript:`. A refused href unwraps the anchor and keeps the text.
- …and that vetting runs BEFORE merge substitution, so a `{{token}}` may decide NEITHER the SCHEME nor the AUTHORITY of an href. The scheme half: `<a href="{{first_name}}">` passed every check and `renderTemplate` turned it into `href="javascript:alert(1)"` on the message detail page, the COM-015 preview and the delivered email alike — `escapeMergeValues` is `escapeHtml`, which has nothing to say about a scheme. The authority half is the same hole one character later: a leading `/` fixes the scheme and NOT the host, so `<a href="/{{first_name}}">` with a value of `/evil.example/phish` renders `//evil.example/phish` — the protocol-relative form `sanitizeUrl` already refuses when it is written literally, and a phishing link in outbound mail. `sanitizeUrl` therefore REFUSES a decoded URL containing `{{` unless the scheme is already fixed by what precedes it — a spelled-out `https?:`/`mailto:`/`tel:`, or a leading `/` — AND refuses `^/\s*\{\{` outright. So `https://example.com/{{email}}` and `/tasks/{{task_id}}` still work, and a bare token or a token that is the whole path does not. Never move the token checks after the scheme check, and never fix this by escaping the value instead: the value is not the problem, the POSITION is.
- **A BACKSLASH IS A SLASH, and the authority refusal covers its backslash spelling too.** Every WHATWG URL parser folds `\` into `/` for an http(s) base, so both refusals above were written in a character the attacker did not have to use: `\\evil.example` resolves to `https://evil.example/` and walked past the literal `//` test, and `/\{{first_name}}` walked past `^/\s*\{\{` (a `\` sits between the `/` and the `{{`) *and* past the `decoded.startsWith("/")` escape hatch, so a merge value of `evil.example/phish` rendered `href="/\evil.example/phish"` and chose the HOST of a link in the delivered email, the COM-015 preview and the message detail page alike. `sanitizeUrl` therefore refuses any decoded URL containing `\` — the check sits IMMEDIATELY after `decoded` is built and BEFORE all four checks below it, because every one of them spells its rule with `/`. A refusal, not a fold: `%5C` is how a real backslash is written in a URL and is untouched, while folding would silently rewrite an author's href. Do not add a fifth special case further down — the point is that nothing downstream ever sees a slash it failed to recognise as one. Pinned in `sanitize.test.ts` and in `cross-surface.test.ts`'s host block, which asserts no surface's rendered href carries `evil.example` **or a backslash**.

## One door in, one door out

- ONE door converts a stored value for reading or editing: `toRichTextHtml` (`format.ts`). It sanitises markup and converts legacy plain text, which is what makes "no migration" true — every template body and every message sent before COM-017 is plain text with newlines.
- That door's markup-vs-prose test is a PARSER's, never a shape's, because the wrong answer DELETES. `isHtmlFragment` matched any `<word …>`, so legacy prose was routed to the sanitiser and truncated: "Bring the <signed lease> and the keys" read back as "Bring the  and the keys", and "if a<b and c>d then stop" as "if a<strong>d then stop</strong>" — silent loss of pre-existing user text on every read surface, which is the exact opposite of the no-migration guarantee. A value is markup only when it opens a tag whose name is a REAL HTML element (`KNOWN_HTML_TAGS`, `sanitize.ts`) and that tag is FINISHED — void (`<br>`), or closed by a `</name>` later in the string. A lone closing tag proves nothing. Nothing this product writes can fall to the prose branch, because `asBlock` block-wraps every value that leaves the door.
- Nothing this product WRITES may be tag-free, and the editor is where that is enforced: it emits `sanitizeEditorHtml` (sanitise, then wrap a bare run in `<p>`), never `sanitizeRichText` alone. The door's plain-text branch exists ONLY for rows written before the feature did — and "text the sanitiser escaped" cannot be told from "text a planter typed in 2025", so a tag-free value gets escaped a second time. An author who types `Q & A` without touching the toolbar leaves a bare text node, which is how `Q &amp; A` reached an inbox, a task detail page and the COM-015 preview alike. Paste is the one caller that still sanitises inline: it inserts a fragment at the caret, and a `<p>` there splits the author's paragraph.
- `toRichTextHtml` is IDEMPOTENT over its own output on every surface — the editor loads it, the send path and `normalizeTaskDescription` store it, the readers render it, and each of those calls it again. Both features are held to it together in `src/lib/rich-text/cross-surface.test.ts`: the message door and the task door must answer the SAME markup for the same body, or one of them has been hardened alone.

## Merge substitution

- Merge substitution into an HTML body is `renderTemplate(html, escapeMergeValues(data))` — the token replacement stays the ONE implementation in `merge.ts`, and only the VALUES are escaped, so a person named `Bobby <script>` is a name. The send path, the COM-015 preview and the message detail page all run those two steps in that order; a surface that runs one of them shows a different email from the one that went out.

## Two columns, two shapes

- A STORED body is TWO columns and they hold two shapes: `communications.body` is the FLATTENED plain text (`richTextToPlainText` of the sanitised HTML) and `communications.body_html` is the markup. `body` is what message SEARCH reads — `ilike(communications.body, pattern)` in `src/lib/communication/filters.ts` — so markup in that column makes a planter's search for "we are excited" miss `we <strong>are</strong> excited` and makes a search for "p" match every formatted message in the church. Both columns predate COM-017; the shape the schema already modelled is the shape the send path writes. `message_templates` carries the same pair, and its editor is still a `Textarea`, so a template writes prose to `body` and leaves `body_html` NULL — which is the legacy row's shape, not a dead column.
- `richTextToPlainText` breaks a line at a block tag's OPENING as well as its closing. A block both ends a line and starts one, and the shape the toolbar produces most often — a typed line, then the bullet button, so no `</p>` stands between the prose and the `<ul>` — flattened to "…and keys- Checklist" when only the closing tags broke: one glued word in the text/plain half the recipient reads, in the `communications.body` column search filters, and on the task card. The doubled breaks that adding the opening rule creates are absorbed by the `\n{3,}` collapse and the `trim()` already at the end of the chain, so nothing else moves.
- ONE read expression, everywhere: `bodyHtml ?? body`, handed to `toRichTextHtml`. That is what makes "no migration" true for messages too — a row sent before COM-017 has `body_html` NULL and prose in `body`, and the door converts it. `resendToNonOpeners` and the message detail page are its two readers today; a third that reaches for `body` alone renders the flattened text and loses the formatting. Pinned in `cross-surface.test.ts` (the stored `body` of a formatted message contains no `<`, and the insert itself is read through `src/lib/testing/source-span.ts`).

## The email artefacts and the RSVP split

- The RSVP placeholders live in `src/lib/email/rsvp-placeholders.ts`, imported by both the email template and `parseRichEmailBody` — the splitter may not import the template it feeds, which is a cycle that loads as `undefined`.
- `parseRichEmailBody` lives in `src/lib/rich-text/email-segments.ts`, beside the sanitiser and the door, because it is a string operation over rich text with no JSX in it. Under `src/components/` it made `src/lib/email/components/communication-email.tsx` depend on `components`. It declares NEITHER of the two decisions it needs: `VOID_TAGS` is imported from `./sanitize` (which imports nothing, so there is no cycle) and "is there anything here a recipient would see" is `isRichTextEmpty` from `./format` — it carried a second copy of each, the void list character-for-character identical and the predicate forty lines from the original.
- `parseRichEmailBody` cuts at the RSVP token by CLOSING every element open at that point and RE-OPENING the same elements after the buttons — never by slicing at the token's raw offset. So every `html` segment is balanced on its own (each becomes its own `dangerouslySetInnerHTML`) AND their concatenation is balanced (they land in one document). A splitter that treats only `<p>` as a block ships `<ul><li>` opened in one segment and closed in the next, which is what a merge field dropped inside a bullet produces.
- TWO MEDIA, TWO RULES, and each medium has exactly one. The HTML half's rule is `parseRichEmailBody`: the COM-015 preview and `CommunicationEmail` both call it over the same sanitised HTML, so a second rule in either place previews a layout the recipient never receives. The text/plain half's rule is `parseBody` (`communication-email.tsx`), which matches the token ANYWHERE on a line, because `richTextToPlainText` writes `- ` before a list item and an equality test against the bare token delivers `__EF_CONFIRM__` as literal text. They differ because their INPUTS differ — markup versus flattened prose — not because one is an exception to the other.
- Those two rules are two COMPONENTS, not one component with a nullable body: `CommunicationEmail({ bodyHtml, … })` renders the HTML artefact and `CommunicationEmailText({ body, … })` the text/plain one, over one shared `EmailShell` (container, rule, footer) and one shared `RsvpButtons`. Neither body prop is optional and no caller passes both — `sendCommunication` renders each artefact with its own call. While it was one component the unused pipeline ran on every render and the props documented a fallback caller that has never existed.

## Block structure and emptiness

- A sanitised body never nests a block inside a `<p>`: `<div>` UNWRAPS when it holds a block child (a contentEditable wraps every list it makes in one, and `<p><ul>…</ul></p>` is invalid), and an opening `<p>`/`<ul>`/`<ol>` implicitly closes an open `<p>`, the way an HTML parser reads it.
- `isRichTextEmpty`, not `.trim()`, decides whether a body is blank. An emptied contentEditable leaves `<p><br></p>`, which is truthy and sends a blank email.
