# Multi-Tenancy

Why and how, for the Multi-Tenancy rules in [`../invariants.md`](../invariants.md). Almost all of it is invitations, because that is the only path that creates a cross-tenant association.

**Source:** `src/lib/invitations/core.ts`, `src/db/schema/*.ts`, `product-docs/system-architecture.md`

A plant's two oversight FKs are **independent associations held side by side**; neither is the route to the other. Isolation is application-layer: a missing `church_id` predicate is a cross-tenant read with nothing behind it to catch the mistake.

## An accept never replaces an association (#265, ruled 2026-08-03)

Nothing stops a second org inviting a plant that already belongs to one, and the plant's planter has authority over that invitation too — so accepting used to set the FK to the newcomer and sever the incumbent silently, with none of the three things #274/OV-007 requires of a sever (type-to-confirm, notification, an `association_events` row).

The guard sits on the **claim**, so a refused accept leaves the invitation `pending` and writes nothing, rather than committing an acceptance with no association behind it. Re-binding the SAME org stays an idempotent no-op — the replay path depends on it. Being a subquery on another table, the predicate alone held only against a *sequential* second accept; [transactions-atomicity.md](transactions-atomicity.md) covers why `lockTargetRow` is what makes it a concurrency guard. `assertConsistent` catches neither case — it inspects one invitation at a time, and two accepted invitations for one slot satisfy "bound IFF accepted" vacuously.

## Open invitations: the register path (#23)

A request with neither target set is legal — the invitee had no account when the admin typed their address, so there is no row to point at. Such a row cannot be accepted as it stands: `verifyInvitationAuthority` compares the actor's org id against `null` and refuses, and `lockTargetRow`/`unboundTargetSlot`/`associationStatement` each throw on a missing target.

Registration binds before accepting because binding leaves the row `pending` with a target, which is recoverable — the planter can answer later — whereas claiming first and creating the organization second would, on a crash, leave an invitation reading `accepted` with no association behind it. `createAccountEntities` therefore sets NEITHER oversight FK.

## No invitation that cannot be answered (ruled 2026-08-04, #23)

The only place an invitation can be answered today is `/register` — the link creates the org and redeems in one request — and somebody who already registered cannot register again. Hence the blanket refusal, placed in the logic layer so a forged direct call is refused too. One message for every account, deliberately: the finer-grained refusals it replaced told an inviter what KIND of account sits behind an address.

Consequently `createInvitation` currently issues only OPEN invitations, and `assertTargetSlotFree`/`heldOversightSlot` are reachable only for a hand-built targeted row until #277 restores the targeted path.

## A token is bound to the address (ruled 2026-08-04, #23)

An invite link is a uuid in a URL — forwarded, pasted, archived — and it buys two things: the association, and (when `BETA_INVITE_CODE` is set) a bypass of the beta gate, which is why both go through one check (`registrationEmailMatchesInvitation`, `(auth)/register/beta-gate.ts`) before the gate and before any account exists. A row with NO recorded address (pre-#23) matches nobody. The register form pre-fills the address `readOnly` — not `disabled`, which submits nothing — but that is convenience: the action is a POST that never saw the form.

## The invitation email: transactional, best-effort, and never logged (OV-003b, #293)

**Source:** `src/lib/invitations/email.ts`, `src/lib/invitations/register-path.ts`, `src/lib/email/redact.ts`

The invitation email is the delivery channel for the token above, so the three rules that govern it belong beside it.

**It is not a notification.** The invitee has no account: no preference row, no category, nothing to unsubscribe from — so `enqueue`, `NOTIFICATION_CATEGORIES` and the dispatcher are all off this path, and the message carries no `List-Unsubscribe` (CAN-SPAM asks for one on commercial mail, not on a message the recipient's counterparty addressed to them personally). The one thing borrowed from the notification channel is `appBaseUrl()`, the repo's single definition of "the absolute base a link in an inbox needs".

**It is best-effort, and the status guard is in the sender.** The row is the durable thing; the email is delivery of a link the admin can also copy. Every failure returns `{ sent: false }` — an email failure that rolled back the invitation would be strictly worse, because the admin's retry then hits the duplicate-pending refusal. `emailSent` is three-valued (`true` / `false` / `undefined` = nothing tried) and must not be collapsed to a boolean on the way to the surface, which reads it through `invitationCreatedNotice` (`create-notice.ts`). The "only a pending invitation is emailed" check sits inside `sendInvitationEmail`, not at the call site, so "a revoked invitation sends nothing further" holds for every caller that ever appears. Re-inviting after a revoke inserts a NEW row with a NEW id, and the URL is a function of that id, so a fresh email cannot carry a dead token.

**The id is a bearer credential, so it is never logged.** It is both the register token and the beta-gate bypass; anyone holding it holds the invitation. So it does not reach `console`, and neither does the URL, the subject or the invitee address — failure logs carry the invitation TYPE and a reason code, which is enough to debug a misconfigured sender and useless to a reader of a log drain.

**One spelling of the link.** `invitationRegisterPath()` lives in `register-path.ts`, which is **import-free on purpose** — the same rule `create-notice.ts` follows. It was born in `email.ts`, which imports `@/lib/email/client` and therefore evaluates `new Resend(...)` at module scope: server-only by construction. A build with the pending list's "Copy link" button importing it from there put `api.resend.com`, `resend-node` and `RESEND_API_KEY` in a 687 KB browser chunk on `/oversight/invitations`. So the client could not use the helper, hand-built the URL, and the "single spelling" was three. `register-path.test.ts` fails if an import appears in the leaf, or if any of the three call sites writes `?invitation=` itself.

**One name for the inviting org.** Two surfaces must answer "who invited them" — this email, and the invitee's register screen (`describeInvitationForRegistration`) — and for a while they answered it twice, with two copies of one policy and the same two queries. `lookupInvitingOrgName` (`core.ts`) is now the only one; `(auth)/register/beta-gate.ts` calls it instead of running its own SQL against another domain's tables, which was a layering violation as well as a duplicated decision. The copies had already diverged in the way that matters: the survivor is exhaustive over `OrganizationInvitationType` and ends in a `const … : never` guard, while the copy took `type: string` and fell through to `null`. Adding a fourth invitation type therefore broke the BUILD in one place and silently blanked the org name in the other — and on that screen a null name is not a cosmetic loss, because `describeInvitationForRegistration` returns `null` for it, so a live invitation stops describing itself and the invitee is dropped into an ordinary beta-gated sign-up. Deriving from `type` rather than from whichever FK is populated is the security-relevant half, for the reason above: `insertInvitation` performs no type↔id consistency check. `org-name.test.ts` fails if a consumer re-reads `sendingChurches`/`sendingNetworks`, or if the survivor's parameter widens back to `type: string`.

## Resending it (ruled 2026-08-10, #293 / PR #392)

**Source:** `src/lib/invitations/core.ts` → Resend, `src/lib/invitations/email.ts` → `invitationEmailIdempotencyKey`, `src/lib/email/client.ts` → `sendEmail`, `src/lib/invitations/resend.test.ts`

Because the send above is best-effort and nothing records its outcome, a failed send used to be recoverable only for the seconds the create notice was on screen: a reload, a navigation or a second create erased the only trace, and the pending list then rendered a never-delivered invitation identically to a delivered one. Four directions were put to the requirement's owner; the ruling was **C — a "Resend email" action on pending rows, nothing persisted**. B (an `email_sent` column plus a badge) was rejected on the merits as well as the cost: `sent` from Resend is *provider acceptance*, not a delivery receipt, so the badge would assert something the product never observes, and it would go stale the moment anyone re-sent out of band.

So the row still cannot TELL an admin that a send failed — it lets them fix it once they know, which also covers the far more common "they say it never arrived". Three properties carry the weight:

**One status decision, still in the sender.** `resendInvitationEmailAs` checks no status of its own. It calls `emailInviteeOutcome` — the same path the create takes, with the reason kept instead of thrown away — and maps the `not_pending` refusal to words through `resendRefusalMessage`. Deleting the guard inside `sendInvitationEmail` therefore fails `resend.test.ts` as well as `email.test.ts`, which is what makes "one decision" a fact rather than a comment. The expiry is the one thing the resend adds, because the sender guards the STATUS and not the window: a pending-but-expired row would otherwise be emailed with a link `bindOpenInvitationTarget` is guaranteed to reject, so it is auto-expired (the existing compare-and-set) and refused.

**A deliberate resend is not a duplicate.** The create has already presented `org-invitation-<id>` to the provider for this invitation — that is what makes a retried create harmless — so a resend presenting the same key is a message Resend may drop while the action reports success. The key stays invitation-scoped (the id is in every key, which is what keeps a re-invitation after a revoke deliverable) and a resend appends a 60-second window bucket. That suffix doubles as the only rate limit the ruling permits: a double-clicked button, or two admins on one page, present one key and the invitee gets one email.

The key is only worth anything if the provider is actually given it, and there are two places that look identical and are not. `sendEmail`'s `headers` argument is the message's own RFC header block, which Resend copies onto the mail and hands to the invitee's client — right for `List-Unsubscribe`, inert for everything else. Request idempotency is `resend.emails.send(payload, { idempotencyKey })`, the SECOND argument, and the SDK builds the HTTP `Idempotency-Key` header from that and nothing else. The key was written into the header map first: it type-checked, it delivered mail, and two sends presenting one key came back with two different message ids — so the window above was inert and a deliberate resend had no limit of any kind. Because the request is now the only reader, a caller-supplied `Idempotency-Key` header cannot reach it and is dropped rather than mailed. `client.test.ts` asserts both halves together, since the earlier regression here was the mirror image: a header map rebuilt for the key silently dropped the opt-out control.

**The button refuses for the rest of the bucket it just keyed (ruled 2026-08-10, round 2).** Round 1 kept the window and left the button live inside it, so a second press reported "Email sent" while the provider collapsed the message onto the one already accepted — the product asserting a send it knew would be dropped. The control is now `disabled` for the remainder of the SAME bucket and its label counts the wait down. That only holds because one piece of arithmetic feeds both consumers: `resendDedupeWindowAt` builds the key suffix *and* the duration the surface counts, in `resend-window.ts` — import-free for the same reason `register-path.ts` is, since the pending list is a `"use client"` module and `email.ts` reaches the Resend SDK. A second `Math.floor(t / W)` anywhere is how the button re-enables a second before the provider will accept a new key. Only DURATIONS cross to the browser (`remainingMs` plus a bucket index used purely as identity), never instants, so nothing on the client is ever asked what time it is on the server; `resendCooldownRemainingMs` owns the "a count belongs to one window" rule, because a count carried over from the previous bucket would start a fresh countdown already spent.

**Named limitation, not an oversight:** the cooldown lives in `useActionState`, which is per client session. A reload, a second tab, or another admin's browser mounts the row with no cooldown, so one press inside an open window still renders "Email sent" over a collapsed message. It cannot be closed here — the server would need a durable last-send record keyed by invitation, which is exactly the persistence round 1 refused, and the provider gives nothing to derive it from (an idempotent replay returns the ORIGINAL response, so `sendEmail` cannot distinguish a new message from a collapsed one). What survives in every case is the half that was always about the provider: the invitee's inbox gets one email per bucket. `resend.test.ts` §8 executes the open case rather than describing it.

**A failed resend is a failed action** — the opposite of the create, deliberately. A create protects a durable row, so its email is best-effort and a failure is reported *alongside* a success (`emailSent: false`). A resend has no artefact to protect: the send is the entire product of the action, so a refusal throws an `InvitationError` whose message the surface renders next to the Copy-link button it names.

Authority is the same `invitingOrgOf(actor)` predicate as the list and the revoke, in the `WHERE` of `orgInvitationQuery` — a screen that shows an admin a pending row and then refuses their Resend is exactly what two definitions of "ours" produce. "No such invitation" and "not yours" are one message, for the reason the respond path gives: an invitation id is also an unauthenticated beta-gate bearer token.

## Slot checked twice; revoke scoped to the org

The create-time refusal is SELECT-then-INSERT, so two racing admins still both get a row. Deleting it loses the legible refusal; deleting the accept-time one loses correctness.

`revokeInvitationQuery` matches on the session's org FK, not `inviter_user_id`, and the surface dropped its per-row `canRevoke`. List and revoke are both built from `invitingOrgOf(actor)` so they cannot disagree about "ours"; any role that does not invite, and any oversight admin with no org, produces `false` and matches nothing.

## Severing does not exist yet — and that is a privacy fact

The `disassociate*` primitives were three of the eleven unauthenticated `"use server"` exports #265 removed, each of which detached any church from its oversight org for anyone who could guess a uuid. They are **not** dead code: ruled 2026-08-03 (#274, `product-docs/features/oversight/frd.md` OV-007/OV-010) that **both sides may sever** — the plant's planter or the org's admin — with the wrappers shipping in #277 and #278. Until then a plant that accepts once cannot withdraw the exposure the ungated portfolio listing gives it (see [hierarchical-access.md](hierarchical-access.md)).
