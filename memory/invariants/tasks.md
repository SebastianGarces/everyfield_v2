# Tasks, Subtasks & Recurrence

Why and how, for the Tasks rules in [`../invariants.md`](../invariants.md). Two features that look separate and are not: **subtasks** (T-016) give a task a checklist, **recurrence** (T-017) mints the next instance on completion — and the interesting rules are where they meet.

**Source:** `src/lib/tasks/` (`service.ts`, `recurrence.ts`, `descriptions.ts`, `templates.ts`, `import.ts`, `phase-prompt.ts`, `dependencies.ts`), `src/components/tasks/`, `src/app/(dashboard)/tasks/`, `src/lib/launch/milestones.ts`, `src/lib/events/subscriptions.ts`

## Subtasks

- **Nesting is one level, refused in both directions.** The arm easy to leave out and fatal to leave out is the demotion: "give B to A" refused but "give A to B" allowed builds the identical tree, and only update can trip it. The check is pure and its loader church-scoped, which is what makes tenancy fall out of it — a parent id from another church reads as *missing*, never as an un-parented task.
- **Ticking the last box does not finish the task.** *Every item is ticked* and *this work is finished* are different claims, and only the planter makes the second, so a fully ticked list points at the Complete button rather than pressing it.
- **The badges mirror the list**, through one exported condition (`topLevelTasksOnly()`) that both the list and the count builders apply; filtering subtasks out of one and not the other prints "1 active / 3 completed" above "Showing 1 of 1 tasks". `listTasks` keeps an `includeSubtasks` escape hatch and `getTaskCounts` deliberately has none, so a badge means the same thing in every view.
- **Checklist work is counted separately**, because two adjacent numbers over one list get read as one population — and scoped by the subtask's **parent**, so an item follows the task it itemises into or out of view.
- **A subtask inherits its parent's assignee as a DEFAULT** (`resolveSubtaskAssignee()`), because with none it is invisible: no "My tasks" view, no filter, nobody accountable. An explicit assignee wins and the subtask stays reassignable. Inheritance, not invention.

### The parent id is a self-FK, `ON DELETE CASCADE` (migration 0038)

The nesting rule is an application rule about DEPTH; until 0038 `parent_task_id` carried no key, so a forged parent id made invisible work — filtered out of `listTasks` by `topLevelTasksOnly()`, reachable only through a parent that does not exist, and still counted by `getTaskCounts`. The FK makes that shape unrepresentable, and the migration nulls dangling parents before adding the key. **CASCADE, not `set null`** — `set null` promotes an orphaned checklist item to a top-level task the planter never wrote; CASCADE says the item belonged to the parent. It fires only where rows are deleted OUTRIGHT (`planWipe()`, hand-run repairs); the product soft-deletes, and `deleteTask` stamps parent and children itself.

## Recurrence

- **A repeating task repeats whole**: the successor carries the checklist with every box unticked. Carrying open items forward needs a per-item "was this ever done" state and makes a half-finished weekly list behave differently from an identical finished one. The Repeat helper text states this, so changing the rule changes that copy.
- **Order is stamped, not defaulted.** One multi-row INSERT gives every `created_at` the same transaction timestamp, leaving checklist order to an `asc(id)` tiebreak over random UUIDs, so `planRecurrenceChildren` sets them a millisecond apart. An item's own due date is dropped: it belonged to the cycle that just closed.
- The checklist copy sits in its own `try`/`catch`, because the successor already exists and a retyped checklist is a smaller loss than a completion that looks like it did not happen.
- **There is no cron** — the next instance exists because you completed the previous one, which stops a repeating task piling up while a planter is away — and `findOpenInSeries` (keyed by `seriesIdOf()`) runs **before** the successor insert, so re-completing an older instance mints neither a second open task nor a duplicate checklist.
- Known gap, carried rather than fixed: that check is a SELECT-then-INSERT, which [`../invariants.md`](../invariants.md) → Transactions names as *not* a concurrency guard. Two racers on one task are safe, because `completeTask` is a real compare-and-set; two instances of one series completed concurrently are not. The honest fix is a partial unique index on the series key for open rows.
- **Only the schedule moves**, and `dueDate` advances from the previous **due date** rather than the completion day, so completing late does not drift the weekday.
- **`completionEvent` is deliberately not carried.** The hook belongs to whatever generated the task, and one is backed by a partial unique index, so copying it aborts the second instance's insert.
- **Completion is written before its successor**, inverting marker-last because the failure modes are not symmetric: a successor with no completion leaves TWO open instances of one series, while a completion with no successor leaves a gap that reopening repairs. `completeTask` swallows a recurrence failure rather than telling the planter their completed task failed to complete.

## Descriptions (T-021)

- A task description uses the same editor and sanitiser as a message body ([`rich-text.md`](rich-text.md)), and `normalizeTaskDescription` is the one write gate. **Enumerate the writers by looking, never by naming plausible ones** — `grep -rn 'insert into tasks' src/` plus every Drizzle `insert(tasks)`. That is how the launch-milestone seeder was found writing authored strings straight into `tasks.description` on a live path. Its sibling `launch_milestones.description` is a different column, rendered as plain text, and does not take the task door.
- The gate is in the SERVICE and not the form, because the task actions are POSTable endpoints that never saw the toolbar. An emptied editor stores NULL, so "has a description" stays one question downstream.
- **`description` means the stored HTML on every row**, with the readable summary beside it as `descriptionPreview` on list rows. One field carrying HTML from `getTask` and plain text from `listTasks` makes the shape depend on which query produced it; the card renders every field as TEXT, so markup there prints `<strong>` at the planter.

## The catalog has two entrances (T-011/T-012)

- The phase prompt is the *timely* entrance and `/tasks/templates` the *standing* one; a planter who declined the prompt or wants an earlier stage's list has no other way in, so the prompt may never be the only door.
- That route is also what makes `importTaskTemplateAction` legal where it lives: with the picker mounted nowhere it is a POSTable endpoint no UI reaches, which [`../invariants.md`](../invariants.md) → Authentication refuses. Unmounting the picker re-opens that finding rather than merely losing a screen.
- `/tasks/templates` is a **static segment beside `/tasks/[id]`**: delete the directory and the URL does not 404 — it resolves to a task whose id is the word "templates" and answers 500. Rendering the component in a test proves the markup, never that a browser can ask for it.

## A phase change prompts; it never creates (T-020)

`phase.changed` has a task-side handler and the handler writes nothing. A planter who advances a stage and finds twenty tasks they did not ask for stops trusting the list with the ones they did; the handler is registered so the place a future author would add auto-creation carries the argument against it.

- **The prompt is derived and only the answer is stored.** `phase_transitions` already records the move durably and the catalog is code, so a pure builder cannot go stale, cannot be half-written by a failed handler, and needed no back-fill. It offers nothing for four distinct reasons, so the caller asks "already answered?" separately: it must tell "answered" (prompt comes down) from "nothing to offer" (leave it up). A backward move still prompts — a planter moving 3 → 2 wants the phase-2 checklist.
- **The answer row is unique on `transition_id` alone**, which re-arms the prompt on the next move and makes the answer belong to the PLANT: the first person to answer answers for everyone, permanently, since there is no un-answer path. Kept on purpose, because a per-person answer means the same 22–26 tasks once per member who visits; widening the key needs the idempotency argument re-made against it, which is a new ruling.
- **The cookie is gone, and the row is the only reader of the answer.** `PHASE_TEMPLATE_PROMPT_COOKIE` shipped as "a fast path and nothing more" and #411 deleted it — the item PR #393 parked, decided on the evidence. It saved no query: `getLatestPhaseTransition` reads the answer in the SAME LEFT JOIN as the transition (read separately, the plant moves in between and a new transition pairs with an old answer), so the query the cookie was supposed to skip is the query the prompt cannot render without. What it cost was a second, weaker source of "already answered" — a year-long browser-held value about an answer that belongs to the PLANT, with no un-answer path — guarded only by a mint rule that shipped wrong once. `markPromptAnswered`, the loader's cookie read, and the second parameter of the three prompt readers went with it; nothing browser-held may answer a prompt again.
- **Accepting claims the row first**, because read-then-import is a SELECT-then-INSERT ([`../invariants.md`](../invariants.md) → Transactions). This inverts marker-last deliberately: importing a checklist is not redo-safe, while a crash just after the claim leaves a transition answered with no tasks — visible, and every checklist still at `/tasks/templates`. A claim whose import wrote nothing is released; one that got part-way is kept, or the planter imports twice. The claim happens after the posted keys are filtered against the live prompt, or a forged POST of bogus keys spends the planter's one answer.
- **"Not now" posts the transition it was rendered for**, because a stale panel otherwise declines, unrecoverably, a stage change nobody was shown. The client may name an id only because it is a guard, not an aim: a value that must equal the server's own latest transition chooses nothing, and the field is required so a POST without it cannot fall back to the unguarded decline.
- **An empty selection is refused, not swallowed**, and "Not now" stays live because an empty selection IS a dismissal. Ticks are counted off the DOM, **but that count has two writers and the second is React**: React 19 restores an uncontrolled form to its `defaultChecked` state once a `<form action>` settles and fires no `change`, so a settle re-ticks every box while a `change`-kept count holds its pre-submit value. Re-reading the DOM after every settle is the subscription case [`../contracts/data-patterns.md`](../contracts/data-patterns.md) allows, not the data-synchronisation it forbids.
- **Every outcome is said out loud**, because a press that writes 22–26 tasks cannot report failure to the console. Three outcomes can live in island state only because each **answers nothing**, so the transition stays open and the next render still contains the panel.
- **A partial import's receipt is server markup, because the island cannot outlive the answer.** Setting a cookie in a Server Action re-renders the page, and a part-way import keeps its claim, so that render builds no prompt and unmounts the island — no revalidation setting keeps a component the server no longer renders. Since #411 the receipt flash is the ONLY cookie this module writes, and it is its own trigger as well as its payload — setting a cookie in a Server Action re-renders the route by itself, with `refresh()` behind it; the receipt is drawn in the no-prompt branch and spent once shown. **It names its own transition**, because a receipt beaten by a newer prompt is never drawn and would otherwise announce a partial import about a press where every clause is false; it cannot be cleared mid-render, since `cookies().set` is Server-Action-only.
- **`refresh()` when something was answered, `revalidatePath` never**, because the planter is standing on the affected route.
- **A decision carries ONE transition id now.** It used to be two — `answeredTransitionId` ("the route changed", drives `refresh()`) beside `fastPathTransitionId` ("this press owns a row", the only field allowed to mint the cookie); they differed on exactly one input, and minting off the wrong one on either button suppressed, forever, a prompt the row said was unanswered. The cookie's deletion removed the second field and the decline `status` that fed it — re-adding either means re-adding a reader, and the only reader it ever had is the thing that was deleted.
- **The decision is a pure function and the action only performs it** — inline in a `"use server"` closure no test can call it, which is how the partial branch acquired a `revalidatePath` nobody could see.
- **One live region, not one per failure**, because each `useActionState` hook keeps its last result forever and two conditionals put two alerts on screen for one press. The empty-tick hint renders unconditionally with its text toggled, since a polite live region inserted with its first message is commonly never announced.
- **Dates come from the transition, not the press**, so answering late gets the schedule an immediate answer would have got; the prompt is re-derived and the posted keys filtered against it. **The prompt states the import policy in its own words**, because `/tasks/templates` adds a second copy while this prompt is answerable once.
- **Two handlers on one event.** `phase.changed` carries the oversight milestone (N-025) and this prompt through `Promise.allSettled`, so neither can cost the other its turn; a single `bus.on` per type would have replaced the first silently.

## What `/tasks` reads off the URL, and off the clock

**Source:** `src/lib/tasks/list-params.ts`, `src/app/(dashboard)/tasks/page.tsx`, `src/components/tasks/task-list.tsx`, `src/components/tasks/task-card-view.tsx`

Three defects of one family — a value taken on trust — and none is visible from the code that suffers.

**The filters were cast, and the route has no error boundary.** `?status=`, `?priority=` and `?category=` were read as `[param].flat() as TaskStatus[]` into `inArray(tasks.status, …)`; the column's CHECK refused a garbage value, so a typo in a shared link rendered the route's own failure. `parseTaskListSearchParams` now parses through the same zod enums the write schemas use and DROPS what it does not recognise — a filter is a view of a list, so an unknown status means the unfiltered list, not a refusal.

**The related-person note was unscoped.** `tasks.related_id` holds whatever the create action was given (`relatedType: "person"` plus any uuid), so `getLatestPersonNote(churchId, personId)` inner-joins `persons` for tenant scope — `person_activities` has no `church_id` of its own, so the join IS the boundary. Unscoped, the page printed another tenant's note on a card, by nothing more exotic than a task pointing at their person.

**The due-date arithmetic read the runtime's clock, twice.** `getDueDateInfo` and `groupTasksByDueDate` each floored their own `new Date()` through the runtime's midnight, so a server-rendered card hydrated to a different "Due today" (React #418) and, on a server east of UTC, every task grouped wrong. `now` is ONE instant minted by `/tasks` in `APP_TIME_ZONE`, and it is REQUIRED — on both functions and on `TaskCardViewProps` — with no clock default even for a surface that never hydrates, because that exemption went stale inside the very pass that wrote it.

**One `as` was left, in the module written to abolish casts.** `parseEnumParam` took a hand-rolled structural stand-in for the zod interface, which discards the parsed type and forces the cast back — letting `parseEnumParam<TaskPriority>(params.status, taskStatusSchema)` compile. It takes `schema: z.ZodType<T>` now and threads `safeParse`'s own `data` through; the three callers INFER `T` rather than naming it.

## Prerequisites (T-015)

**Source:** `src/lib/tasks/dependencies.ts`, `src/db/schema/tasks.ts` (`task_dependencies`)

- **Blocked is derived.** An incomplete live prerequisite is the blocked state; nothing writes `tasks.status = 'blocked'` on the planter's behalf. Completing the last one clears the badge on the next render (`refresh()` after `completeTask`), which is why the list re-asks the edge table rather than trusting a stored flag that would need its own write.
- **Church scope is the row.** Composite FKs onto `tasks(id, church_id)` make a cross-church edge unrepresentable. The write is still `insert … select` joining both ends on `church_id`, so a forged id that names no live row in this church inserts nothing — the same shape as `createHouseholdWithHead`.
- **Cycles are refused before the write.** The CHECK only sees a self-loop; A→B→A and longer chains are `wouldCreateCycle` over the church's existing edges plus the proposed set. A SELECT-then-INSERT, so two concurrent opposite edges can still land — the unique index only stops a duplicate of the same pair.
