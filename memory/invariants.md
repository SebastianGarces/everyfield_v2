# Invariants

**Every rule is stated below, one line each — these lines ARE the rules**, not a table of contents for them. Read only this file and you have still seen every rule.

Rules bind at two strengths (`ops/agent-os/delegation-rules.md` R6):

- An **untagged line is an invariant** — a mechanical or security fact. Never break it; a change that needs to is wrong.
- A line tagged **⚖ is a ruling** — a dated product decision. Never break it *silently*: build to it, and if it no longer fits what you are building, raise a spec-question hold with options instead of deviating. A new ruling changes it; nothing else does.
- A line starting **Accepted residual** is a known gap, carried deliberately until the named condition retires it.

Each section links `invariants/<domain>.md` for the why, the pattern and the worked examples. Read the domain file when you are touching the files it names; read all of them if you are the security lens or resolving a `memory/` conflict.

## Transactions / Atomicity

→ [transactions-atomicity](invariants/transactions-atomicity.md) — any DB write path.

- `db.transaction()` throws at runtime; neon-http has no interactive transactions. Never call it.
- All writes known up front → one `db.batch([...])`: a Neon batched transaction, all-or-nothing.
- That rule is checked over SOURCE (a unit test cannot execute a write), and the three regexes that check it have ONE implementation: `assertBatchedWrites(body, label)` in `src/lib/testing/db-atomicity.ts`, fed a body cut with `sourceReader` (never a bare `indexOf`). `transitions/service.test.ts` and `signals/attestation-service.test.ts` shipped identical copies in one commit — widen one to catch `db.execute` or a `.transaction(` split across a newline and the other keeps passing a narrower rule on the module it guards.
- Writes interleaved with reads, events or another feature: write the durable "already happened" marker LAST, every earlier step idempotent.
- Marker-last assumes the earlier steps ARE redo-safe. Where they are not — a template import creates a second copy by design — the marker becomes a CLAIM written FIRST (`ON CONFLICT DO NOTHING` against a unique index) and the non-idempotent work is gated on the claim's own rowcount. `acceptPhaseTemplatePrompt` + `phase_prompt_answers_transition_unique_idx`.
- SELECT-then-INSERT is not a concurrency guard. Make duplicates impossible with a (partial) unique index, keeping that row in the SAME `INSERT` as the rows it speaks for.
- In a batch the compare-and-set goes FIRST and the dependent write's `WHERE` re-asserts what the claim set — an empty `returning()` is not an error and rolls nothing back.
- A compare-and-set serialises only same-row writers; a predicate about another table is a snapshot read. To compete for a row elsewhere, `SELECT … FOR UPDATE` it as statement ONE and gate on the dependent write's own rowcount.
- In a `WITH` chain a `FOR UPDATE` snapshot CTE must be a DEPENDENCY of the write (`update … from current c`), never a sibling only the journal joins — pulled lazily after the UPDATE it reads nothing, and the history row is silently lost.
- A plant declares its starting phase ONCE, and the DATABASE is what says so: `phase_transitions_initial_declaration_unique_idx` (partial, on `church_id where kind = 'initial_declaration'`) plus `ON CONFLICT … DO NOTHING` — never a `NOT EXISTS` over `phase_transitions`, which is the same-lock-different-table trap and was raced into fabricating history.
- A church and its `church_privacy_settings` row are created by ONE batch; the loser's orphan church is swept afterwards under a `NOT EXISTS` guard.
- Both answers to an empty planter seat — the No as well as the Yes — open with `SELECT … FROM churches … FOR UPDATE` and are gated on their own rowcount.
- `finalizeAttendance()` emits downstream first, then compare-and-sets `actual_attendance` (non-null = finalized = its idempotency key); `meeting.attendance.finalized` is emitted STRICTLY.
- `createHouseholdWithHead` (src/lib/people/household.ts) is ONE `db.batch` whose household INSERT is an `insert … select` sourced FROM the person row — the person existence check IS the insert's row source, so never re-add a pre-flight SELECT. The household INSERT must stay FIRST: `persons.household_id` FKs `households.id`, so the person update needs the household row to already exist in the batch.
- Accepted residual: the two `createHouseholdWithHead` statements take separate READ COMMITTED snapshots, so a person soft-deleted between them commits an orphan household — the JS `throw new Error("Person not found")` fires after COMMIT and rolls nothing back (the "empty `returning()` rolls nothing back" rule above).
- Accepted residual: the COM-020 task→communication log entry has only a SELECT-then-INSERT on `communication_recipients.external_id = 'task:<id>'`; `completeTask` is a read-then-write, so a double-clicked Complete writes two entries until a partial unique index exists.
- Accepted residual: `meeting.attendance.recorded` is non-strict — a failed prospect → attendee advance is swallowed rather than blocking finalization.

## Multi-Tenancy

→ [multi-tenancy](invariants/multi-tenancy.md) — invitations, associations, onboarding.

- All feature data carries `church_id`; `church_id = null` means global content (e.g. wiki articles).
- Tenant isolation is enforced in the application layer — there is no RLS behind you.
- A person-scoped write whose service does not itself scope the person by church calls `assertPersonInChurch(churchId, personId)` (src/lib/people/service.ts) FIRST — tags, skills and commitment uploads stamp the caller's church_id onto a client-supplied person_id and would otherwise write across tenants; the commitment check precedes the file upload so no object lands for a foreign person.
- Hierarchy is SendingNetwork → SendingChurch → Church, every hierarchy FK nullable, and a plant's two oversight FKs are INDEPENDENT — neither implies the other.
- An accept never replaces an existing association: both statements of the accept batch carry `fk IS NULL OR fk = <this org>`, and the guard sits on the CLAIM so a refusal writes nothing at all.
- An invitation may name no target — that is the register path. Only `bindOpenInvitationTarget` (CAS on pending + both targets null + unexpired) gives it one, which is what makes a link single-use; registration binds BEFORE accepting, never after.
- ⚖ An existing account MAY be targeted (#304 built the surface that answers), but EVERY refusal reachable AFTER the address has been resolved to a target is the ONE message, `ACCOUNT_NOT_INVITABLE_MESSAGE` — not merely the three the ruling listed ("not invitable" / "slot held by another org" / "already ours"). The property is positional, not a list: anything downstream of `resolveInvitationTarget` speaks about a STRANGER, so `assertTargetSlotFree` has no message of its own (`slotRefusalMessage`) and the second authority pass goes through `resolveInvitationForResolvedTarget`, which collapses it. Only the target-less AUTHORITY pass, which runs before any lookup and describes the ACTOR's own role and org, stays legible. Add a rule downstream and it is collapsed by construction; add one that reads the address by another route and it is yours to collapse.
- ⚖ No invitation that cannot be answered, and it is now TRUE FOR ALL ROLES: every TYPE that can name an existing account has an in-app surface for the role that answers it, AND that role can leave the association from the same surface. `church_to_sending_church` / `church_to_network` → the planter, at `/settings/association` plus the dashboard reminder, with `LeaveOrgDialog`; `sending_church_to_network` → the target sending church's admin, at the same route's second view, with `LeaveNetworkDialog` (#304 WS3 / OV-013). `/settings/association` serves both roles and `/settings` links it to both; adding a fourth invitation type means adding its answering view AND its leave control in the same change (`answer-surfaces.test.ts` enumerates the type list and fails otherwise).
- The two leave endpoints are separate, and neither takes an entity id: the planter's takes a two-valued KIND (a plant has two associations to choose between), the sending church's takes NOTHING (a sending church has exactly one, always with a network). One shared endpoint with a role branch would put the choice of authority rule in the client's hands.
- ⚖ One inviting org may address ONE email at most `INVITES_PER_INVITEE_PER_WINDOW` (3) times per `INVITATION_EXPIRY_DAYS`, counting EVERY status — a targeted invitation raises a dashboard reminder that is dismissible only by answering, so a decline–reinvite loop would be a permanent attacker-chosen banner. The cap runs BEFORE `resolveInvitationTarget` and applies to open invitations too, or "this address is rate-limited" would itself say an account exists.
- ⚖ …and it RESETS AFTER A SEVER (ruled 2026-08-11, round 10): both count queries drop every invitation older than that org's most recent `association_events` row about the same subject (`afterTheLastAssociationEventFilter`, one predicate shared by the address scope and the target scope). The cap needs BOTH justifications — a decline writes no event, so the decline–reinvite loop stays capped, while an association that was accepted and later ended refunds what it spent, or the three severs #304 ships would lock an org out of re-inviting a plant it legitimately parted with and `INVITE_RATE_LIMITED_MESSAGE` would assert a pending answer with nothing pending.
- Both create-time caps count the resolved TARGET as well as the address (`targetReachFilter`, shared by `assertTargetInviteRateLimit` and `assertNoDuplicatePending`): one organization can be reached through several accounts, so an address-only cap is spent by typing a second admin's email. The target-scoped refusal is `ACCOUNT_NOT_INVITABLE_MESSAGE`, never the legible cap message — it fires post-resolution, and naming it would say two addresses belong to one org.
- The two rate-limit passes are two FUNCTIONS, not one called twice: `assertInviteRateLimit` (address scope, the only place `INVITE_RATE_LIMITED_MESSAGE` is composed) runs pre-resolution, `assertTargetInviteRateLimit` runs post-resolution and contains no legible message to throw. While they were one function the second call re-ran the address count and could emit the legible refusal from the collapsed path; the guarantee is now a property of the call graph rather than of the call order.
- A client NEVER names an invitation's target. `resolveInvitationForResolvedTarget` builds its request key by key from the server-resolved target (no `{...request}` spread — a spread contributes nothing when the target is `{}`, so a forged key survives it), and `createInvitationAs` strips the keys at the call site too. Every `"use server"` export whose parameter is a typed OBJECT parses a strict zod schema first (`z.strictObject`, after the session check) — a TypeScript parameter constrains a forged body not at all.
- ⚖ The create-invitation success notice shows ONE neutral message for both kinds of invitation and never asserts whether an account exists; the action's success payload carries no target-derived field. A branching success answers the same question the collapsed refusal hides, for free.
- ⚖ The rule covers the WHOLE `/oversight/invitations` page, notice AND pending list: nothing derived from `target_church_id` / `target_sending_church_id` may reach the client (no `isOpen`, no per-row control that varies with it), and no admin-facing surface renders a `/register?invitation=` link. A control shown on the open rows only is the same oracle as a branching sentence, read off the row the admin just created.
- ⚖ The rule is TRANSITIVE, and `type` is target-derived: `resolveInvitationRequest` picks the kind from the resolved target and falls back to the admin's `inviteAs` only when there is no target, so a row caption off `invitation.type` (`kindLabel`) matched the admin's own selection for an accountless address and FLIPPED for one holding an account of the other kind. An `InvitationListRow` carries only what the admin themselves typed plus the invitee's own answer — five fields, built by `toInvitationListRow` (`src/lib/invitations/list-row.ts`), never inline in `page.tsx`.
- Pin this rule by CALLING the row mapper, never by grepping the page. Regexes for `targetChurchId` / `isOpen` plus an allowed-field set that whitelisted `kindLabel` all passed while the property was false, twice; `invitations-ui.test.ts` §9b now resolves both target shapes and asserts the two rendered rows are deep-equal, which is what sees a derivation through an intermediate column.
- ⚖ The rule reaches `/register` ITSELF, and BOTH readers of the row on that route (ruled 2026-08-11 round 10, extended 2026-08-12 round 11). The two verbs have DIFFERENT indistinguishable sets and neither list may be read as the other's: **the GET must render identically for {a targeted invitation, an answered one, a nonexistent id}** — an OPEN row does NOT join that set, it renders the redeeming form, which is the accepted residual below and not a closure; **the anonymous POST must respond identically for {a targeted invitation, an open one submitted with a NON-matching address, an answered one, a nonexistent id}**. ONE exported predicate decides it — `isOpenRedeemableInvitation(invitation, now)` in `register/beta-gate.ts`: pending + unexpired + non-empty `invitee_email` + BOTH target columns null — and `describeInvitationForRegistration` (what the page renders) and `hasValidInvitationBypass` (whether the beta gate is skipped) both call it. Never a second copy of those four clauses. The invitation id is in the inviting admin's DOM by design (Revoke needs it), so "no admin surface renders the link" is NOT the boundary.
- THE BYPASS WAS THE MISSED READER, and the reason is worth keeping: an invitation token buys TWO things on `/register` — a described invitation and a beta-gate bypass — and round 10 fixed only the first. `hasValidInvitationBypass` read the same row by a second route with its own copy of the rule, so with `BETA_INVITE_CODE` set the session-free POST still answered a targeted id ("an account with this email already exists"), an open one (registered) and a guessed uuid (`BETA_GATE_ERROR`) three different ways. When a rule is about a ROUTE, enumerate that route's readers of the row; one reader fixed is a rule half-recorded.
- ⚖ The anonymous `/register` POST returns NO per-row message (Ruling C, 2026-08-12): a wrong-address submit falls through to the ordinary sign-up exactly as an unknown id does, and `invitationEmailMismatchMessage` has no caller on that action. `invitationActedOnAtRegistration` makes the decision ONCE and every later branch — the gate bypass, "name your church plant", the redemption — reads that one result, never the submitted `invitationId`. The 2026-08-04 binding ruling is untouched: redemption is still gated on the invitation being non-null. The message returns only behind a session, on an invitee-proven surface.
- Accepted residual — an OPEN row is distinguishable at `/register` in TWO ways, and both are inherent to invite-at-registration. (1) THE GET, which is a READ-ONLY probe needing no address and no session: `register/page.tsx` calls `describeInvitationForRegistration` and hands a non-null result to `RegisterForm`, which renders the inviting org's name and the pre-filled `readOnly` address — so an open id shows the redeeming form where a targeted / answered / nonexistent id shows the plain page. That is the round-10 attack verbatim, still live for one of its four inputs, and an open invitation MUST be usable at `/register`, so it cannot be closed on this route. (2) THE POST with the MATCHING address, which redeems — an invitation being CONSUMED (a write, audited, single-use) rather than a row being read. What round 11 closed is the POST for every NON-MATCHING address; do not read "both readers call one predicate" as "both verbs answer identically". It retires only if invite-at-registration does.
- Pin BOTH readers by CALLING them, never by a regex over the source. Regexes for `targetChurchId` / `isOpen`, an allowed-field whitelist, and three source-text assertions over `register/actions.ts` have now all passed while the property was false — four times in one track. `invitations-ui.test.ts` §9c calls `describeInvitationForRegistration` AND `hasValidInvitationBypass` through `RegistrationInvitationReader` over rows the real resolver produced, and `scripts/g3-association-lifecycle.ts` §11 calls both against real rows with the gate on.
- `redeemable` is deleted rather than left constant; `accountType` survives only because every described row is open, where `type` is the admin's own `inviteAs`.
- ⚖ `association_events` names a SUBJECT, not a plant (ruled #351, migration 0036): `subject_type` ∈ {church, sending_church}, one nullable FK per kind, and a CHECK that exactly one is set. `church_id` is nullable HERE and that never means "global content" — the CHECK makes a subject-less row unwritable. All three invitation types audit; `auditableAssociationOrg` returns a subject for each.
- ⚖ A notification is anchored to a CHURCH or to an ORG (`anchor_type` ∈ {church, sending_church, network}, `anchor_org_id`, CHECK exactly-one) — ONE table, never a parallel org table. Every church-scoped read still names `church_id` and is unchanged; the org reads name `anchor_org_id`; neither coalesces, so the two tenancies partition the table.
- The org anchor gets its OWN unique index and its own ON CONFLICT clause, on a single NON-NULL `anchor_org_id`. Two nullable per-kind columns would have put a NULL in every org row's index key, and NULLs never collide in a btree unique index — `dedupeKey` would have stopped being idempotent for exactly the rows #304 WS3 adds.
- Gate 1 for an org-anchored row is `recipientAdministersOrg` — this user's own org FK equals the anchor AND their role is the one that administers THAT KIND of org (`sending_church` → `sending_church_admin`, `network` → `network_admin`) — NOT `canAccessChurch`, which has no plant to traverse. "Any oversight role" is too coarse: both org FKs live on one `users` row, so a network admin carrying a stray `sending_church_id` would receive that sending church's own rows, which is the hierarchy walk this rule forbids. `listOversightAdminsOfOrg` pairs role with FK inside each arm so the audience and the gate cannot disagree. Consent has no third party to come from, so a category that requires sharing is refused outright.
- The role↔org-kind↔FK pairing is ONE TABLE, `OVERSIGHT_ADMIN` (`src/lib/notifications/oversight-admin.ts`), keyed on `AssociationOrgType` with each row `{ role, fk }`, and the shape its readers pass around is derived from it (`OversightOrgIds`, built by `noOversightOrg`/`oversightOrgOfKind` — "only" INSIDE `src/lib/notifications/`; `announceAssociationEndedFor` in `src/lib/invitations/core.ts` still hand-builds one, compile-guarded but able to file an id under the wrong FK, and `oversight-admin.test.ts` §3 cannot see it). No reader in `src/lib/notifications/` writes an oversight role literal or an oversight FK column name — audience, gate, inverse lookup, both relationship probes and every audience constructor index or enumerate the table (`memory/invariants/multi-tenancy.md` enumerates them; `oversight-admin.test.ts` §3 sweeps their source, beside the table's own obligations rather than in a reader's suite). The ONE exception is which `churches.sending_*_id` column stands for each `users` FK, which the table does not hold. A SQL builder and a TypeScript predicate cannot share an implementation, but they must share the DECISION: while it was written per site they drifted, and the drift starved a plant of its daily digest.
- That table is a TYPE-IMPORT-ONLY leaf and its roles are tied to `OVERSIGHT_ROLES` (`src/lib/auth/access.ts`) by test, not by copy — `oversight-admin.test.ts` §1 fails on divergence in either direction, §2 on any value import. The builder is OVERLOADED (non-nullable refs in → `SQL` out) and the digest holds `const owedDigestAudience: SQL`, so the mistake is a compile error.
- No `inArray(role, OVERSIGHT_ROLES)` floor beside that audience: each arm already names its role from the pairing table, so the floor is dead SQL, and an arm edited to a non-oversight role would be silently ANDed to zero rows — a loud bug turned into an empty audience.
- A decline names the ADDRESS THE ORG TYPED, never the plant: the refused org never associated with it, so `invitee_email` is the only identifier that goes back. Every OTHER milestone names the plant, which is why the field is `MilestoneFacts.subject`, not `plantName`.
- `status = 'pending'` is not "answerable": expiry is LAZY (a row is stamped `expired` only when somebody tries to answer it), so every list that OFFERS an answer carries `(expires_at is null or expires_at > now)` too — `getPendingInvitationsForPlant` included, because its reminder is dismissible only by answering.
- An invite token is bound to the invited ADDRESS, not the link holder: the registering email must equal `invitee_email` (trim+lowercase) for both the association and the beta bypass. Fix a wrong address by revoking, never by re-aiming a live invitation.
- The invitation email is TRANSACTIONAL and deliberately bypasses the notifications machinery — no category, no preference gate, no `enqueue`, no `List-Unsubscribe`. The invitee has no account, so there is no preference row to consult; `sendInvitationEmail` (`src/lib/invitations/email.ts`) borrows only `appBaseUrl()`. It is also best-effort: a refused or thrown send returns `{ sent: false }` and NEVER fails the create.
- The invitation id is a BEARER CREDENTIAL — the register token and the beta-gate bypass — so neither it nor any URL built from it reaches a log, an error message or an analytics event. Failure logs carry the invitation TYPE and a reason code only; `redactForLog` (`src/lib/email/redact.ts`) is what the email client logs through.
- The `?invitation=` link has ONE spelling — `invitationRegisterPath()` in `src/lib/invitations/register-path.ts`, an IMPORT-FREE leaf. Its only caller is the invitation EMAIL; no admin surface builds the URL at all (the ruling above). The leaf stays separate anyway: `email.ts` builds a Resend instance at module scope, so importing the spelling from there would ship the SDK into any page chunk that wanted it. Never re-spell the query key — AND NEVER RE-EXPORT IT: `email.ts` carried `export { INVITATION_REGISTER_PATH, invitationRegisterPath }` for callers that did not exist, which made `import … from "@/lib/invitations/email"` type-check and work and put the ~687 KB SDK one import away from any client component (only `invitations-list.tsx` was guarded). A leaf whose contents are also served from the trunk is not a leaf. `register-path.test.ts` §2 now enforces the property instead of the instance: exactly ONE module in `src/` exports either symbol, and nothing under `src/app/` or `src/components/` may import them from anywhere but `@/lib/invitations/register-path`.
- "Is the slot free" is asked twice and the two are not interchangeable: at create for a legible refusal, at accept as the real guard.
- The inviting org's name comes from `invitation.type`, never from whichever FK is set, and there is ONE implementation: `lookupInvitingOrgName` (`src/lib/invitations/core.ts`), exhaustive over `OrganizationInvitationType` with a `never` guard. No surface — the email, the register screen — queries `sendingChurches.name`/`sendingNetworks.name` for it itself; the copy is always the one that misses the fix. `/register` reaches it through `registrationInvitationReader`, whose default IS that function.
- An invitation belongs to the inviting ORG, not the admin who typed it — list, revoke and resend share ONE predicate, `invitingOrgOf(actor)`.
- ⚖ A pending invitation carries a "Resend email" action so a failed or missed send is recoverable at any time (ruled 2026-08-10 on #293/PR #392). NOTHING is persisted about delivery — no `email_sent` column, no badge; provider acceptance is not a delivery receipt, so a stored flag would assert what the product never observes. `resendInvitationEmailAs` adds NO status rule of its own: it calls the same send path and turns `sendInvitationEmail`'s `not_pending` refusal into words.
- A deliberate resend must never be deduped away by the provider: the `Idempotency-Key` stays INVITATION-scoped but a resend adds a window suffix (`invitationEmailIdempotencyKey`, `RESEND_DEDUPE_WINDOW_MS` = 60s), so a double-clicked button sends once and a genuine second attempt reaches the invitee. Reusing the create key would report success over a message the provider dropped — the exact failure the button exists to repair.
- ⚖ After a successful resend the button is DISABLED for the remainder of that same 60s bucket and counts it down (ruled 2026-08-10 round 2). Only DURATIONS cross to the browser, never instants, so a skewed workstation clock still waits the right length.

## Authentication

→ [authentication](invariants/authentication.md) — sessions, `"use server"` modules, route handlers, `src/proxy.ts`.

- Session-based, NOT JWT, for immediate revocability; `sessions` is keyed by the hashed token.
- Cookie `session` (httpOnly, secure in prod, sameSite=lax); 30-day expiry, 15-day sliding refresh.
- The `sessions.fresh` column exists, but the freshness control is deliberately unwired — no helper, nothing gates on it — until the first sensitive op ships (ruled 405-2b, 2026-08-12).
- **Every export of a `"use server"` module is a POSTable endpoint reachable with no session and no UI** — the export list IS the auth surface. Keep helpers, reads and not-yet-wired writes in a sibling module with no directive.
- A state-changing action never takes its actor as an argument — it mints one from `verifySession()`. An entity implied by the actor (their own plant, their own org) is not an argument either.
- SESSION FIRST, THEN THE PARSE: the mint is the FIRST statement of the export, ahead of `safeParse` (ruled 2026-08-10 on #304). Parsing first is not usually exploitable, but it answers a sessionless caller differently for a malformed argument (`{ success: false }`) than for a well-formed one (a throw) — a free shape-oracle — and it makes "does this endpoint check anybody?" a question about reading order instead of about line one. `service.test.ts` §1b/§1b′/§1b″ calls every invitation-domain export with no session, with BOTH argument shapes — strings for the association surfaces, real `FormData` for the `useActionState` ones. The guard may be a DUPLICATE of a mint the service already does (`oversight/invitations/actions.ts` checks, then passes nothing down): the session read is `React.cache()`d, so it costs no second query, and the module-level guard is what answers the anonymous caller before the parse can.
- WHAT IS PINNED REPO-WIDE is that ORDER — the mint precedes `.safeParse(` in every parsing export of every `"use server"` module under `src/` (round 8, 2026-08-10). `src/lib/auth/server-action-surface.test.ts` WALKS them all, matches braces to read whole bodies, and derives what counts as a mint per module (`verifySession`/`getCurrentSession`, plus any local or imported helper that reaches one — `currentViewer`, `requireChurchSession`, `requirePlatformAdmin`). Twice the rule was written down as universal while a file list made it domain-wide, and both times the unlisted modules were the ones parsing first — five of them at round 7. The only exemption is the `(auth)` and `(marketing)` route groups, whose endpoints are public by construction, and the exempt set is asserted EXACTLY (`login`, `register`, `requestInviteAction`) so the group cannot become a hiding place. An endpoint the walk cannot READ is banned rather than trusted: the matcher reads `export (async) function NAME(…)`, so `export const fooAction = async …`, `export default`, and `export {…} from` are refused by name in a `"use server"` module (none exist today).
- A NEW action mints ABOVE the `try`, not merely first inside it, so a sessionless call THROWS instead of being converted into a handled `{ success: false }` by a catch — the shape `settings/actions.ts`, `settings/sharing/actions.ts`, `notifications/actions.ts` and the three invitation modules have. NAMED RESIDUAL (round 8, 2026-08-10): 45 older exports across nine `(dashboard)` modules (people 13, meetings 12, teams 9, tasks 6, phase 3, feedback 1, launch 1) mint INSIDE their `try`, so an anonymous POST gets `{ success: false, error: "You must be logged in …" }` rather than a throw. That is NOT a hole — the mint still precedes the parse, so a well-formed argument and a malformed one get the identical answer, there is no shape-oracle, and nothing is read or written — so it is recorded rather than rushed. The residual is listed EXACTLY in `TRY_WRAPPED_MINTS` and asserted with `deepEqual`, so an unlisted try-wrapped action fails `pnpm test` instead of quietly joining the group. It retires when those nine modules lift the mint above the `try`: empty the list and the above-the-`try` form becomes the universal assertion.
- A shared secret is never compared with `===`: use `matchesBearerSecret`/`constantTimeEquals` from `src/lib/security/constant-time.ts`, which hashes both sides to a fixed length first. Covers `CRON_SECRET` and `REVALIDATION_SECRET`.
- A request header the app does not write UNCONDITIONALLY is client input and nothing may branch on it. The trusted headers are `x-pathname` (`PATHNAME_HEADER`, absence fails closed) and the platform-written `x-real-ip`.
- Client IP resolution reads `x-real-ip` first, then falls back to the LAST hop of `x-forwarded-for` — never the first hop, which the client writes (`getRequestIp`, ruled 405-1a, 2026-08-12).
- The crawler allowance is ONE predicate, `isCrawlerPreviewRequest(userAgent, pathname)`, over a fixed route list that is a STRICT subset of the protected list — `/wiki` only. It buys the unauthenticated shell, never a session and never per-user data.
- Listing a route there means "this route produces a session-less render worth previewing" (ruled 2026-08-09): it must render with no session AND that render must be the page, not a redirect. `/dashboard` failed the first (it calls `verifySession()`, so crawlers 500'd); `/oversight` failed the second (its pages redirect to /login, so no card was ever produced).
- Both stay in the proxy's `PROTECTED_ROUTE_PREFIXES`, named EXPLICITLY and not through the spread of the previewable list — dropping a prefix from that list must never unprotect the route as a side effect.
- The `whatsapp` crawler token is anchored — `^whatsapp/<digit>`, which is WhatsApp's link-preview FETCHER, whose UA is only the token. Its in-app browser is a human behind a `Mozilla/5.0 …` UA that also says WhatsApp; a bare substring called that person a bot.

## Phase Engine — Cited Facts & Attestation Citations

Applies to `src/lib/phase-engine/{fact-format,fact-phrases,attestation-citation,manual-signals}.ts`, `src/lib/phase-engine/assessment/{snapshot-fact,exit-criteria}.ts`, `src/lib/phase-engine/signals/{build-fact-snapshot,attestation-service}.ts` and the three `/phase` surfaces that render `plant_insights.cited_facts` (`components/phase-engine/{csf-scorecard,insight-card-view,exit-criteria}.tsx`). Ruled on #319 across three rounds (2026-08-10 / 2026-08-12); the rows are `PR 394 (a)/(b)/(c)` in `product-docs/decisions.md`.

Those three lib modules are ONE concept each and the split is load-bearing: `fact-phrases.ts` is the phrase VOCABULARY (one entry per snapshot path, grows when the snapshot grows), `attestation-citation.ts` owns the attestation TAXONOMY (both legal spellings, and the leaf table), and `fact-format.ts` is the MECHANISM (parse → classify → dispatch → render). Never re-add an attestation leaf to `FACT_PHRASES`, and never spell either prefix outside `attestation-citation.ts`.

- THE MANUAL-SIGNAL VOCABULARY IS ONE DECLARATION AND IT BINDS THE WRITER TOO — `MANUAL_SIGNALS` in `src/lib/phase-engine/manual-signals.ts` (import-free, because a `"use client"` island renders it), one object literal per signal holding ALL FOUR of its strings: `key`, `label`, `description` and the `clause` a citation of it reads back as. The clause lived in `fact-phrases.ts` tied by a `satisfies Record<ManualSignalKey, string>`, which catches a MISSING clause and cannot catch DRIFTED WORDING — the only property the pair exists for, since the evidence a planter is shown must use the words of the control that produced it; `MANUAL_SIGNAL_CLAUSES` is now a `Map` BUILT from that table and adding a signal is one edit in one file. The three READERS are typed against `ManualSignalKey` (`attested()` in `assessment/exit-criteria.ts`, the clause map, the toggle card) and the WRITER is bound at runtime: `setManualSignalSchema` is a `z.enum` over `MANUAL_SIGNAL_KEYS`, which stays a plain `readonly ManualSignalKey[]` — zod 4's `z.enum` takes `const T extends readonly string[]`, so no non-empty-tuple assertion is needed and none may be re-added (an `as [K, ...K[]]` cast drops the `readonly` and asserts a non-emptiness TypeScript cannot check). While it was `z.string().min(1).max(100)`, `setManualSignalAction` — an export of a `"use server"` module, so a public POST with no UI in front of it — stored `{signalKey: "systems_testd"}`, the snapshot folded it in as an attested fact of the plant, and the citation printed "you confirmed systems testd" with no gate behind it: the failure the module's own docblock was written to make impossible, reachable by input instead of by a developer mistake.
- A manual attestation is citable TWO legal ways and BOTH are correct: `signals/build-fact-snapshot.ts` writes the manual block twice (`manual.byKey.<signal>` and `manual.attestations[]`) and the judge's citable ledger is the whole flattened snapshot. Which spelling arrives is the model's coin-flip, so nothing downstream may depend on it.
- ⚖ ATTRIBUTION resolves the array spelling onto its signal: `attestationSignalKey` reads entry N's `signalKey` out of the assessment's OWN snapshot and `normalizeManualCitation` rewrites the citation to `manual.byKey.<signal>` before a criterion is matched. Never a bare `manual.` prefix rule — each attested gate measures ONE signal, so a prefix would light all three for a citation about any of them.
- An UNRESOLVABLE row (out-of-range index, non-numeric index, no `signalKey`) attributes to NOTHING and is never guessed onto a gate; the criterion then reads `not_addressed`, which is the honest answer.
- ⚖ WORDING is unified across all three surfaces from that same reading, and it is a READ-LAYER fix because a component holds no snapshot: `resolveCitedFactSignals` → `AssessedInsight.citedFactSignals` → `formatCitedFacts(citedFacts, signals)` on the card and the scorecard, `formatCitedFact(fact, { signalKey })` on the drill-down.
- ⚖ The folding path is a COUNTER and MUST NEVER BECOME A LISTER: one distinct attestation in a group reads the drill-down's own sentence, and the moment two disagree the group collapses to a count ("3 things you confirmed"). "Improving" `formatCitedFacts` to name the things it counts is the change this ruling forbids — it turns a chip that says how much evidence there is into a second copy of the drill-down.
- The fold is keyed on the RESOLVED SIGNAL, never on the rendered phrase — that is what makes the rule spelling-independent at every N: two attestations count the same whether cited by key or by row, and one attestation cited BOTH ways is one thing, not a named sentence beside a count that already included it.
- That takes TWO keys and BOTH are required. A group's IDENTITY is the leaf's own `groupKey` — template plus value-class (`attestation:value:true` / `:false` / `:other`, `attestation:signalKey`, `attestation:attestedAt`), signal-free and date-free by construction; its MEMBERS are the distinct resolved signals. Never `renderPhrase(group, 1)` for an attestation: two of the three leaves bake the signal (`signalKey`) or the date (`attestedAt`) INTO the phrase, so a phrase key gave every attestation a group of its own and the counter printed each one's sentence — a lister on every leaf that names its signal or its date, with a valueless array `signalKey` falling out of the templates and printing "signal key (manual attestations)".
- ⚖ THE LEAF TAXONOMY IS ONE TABLE — `ATTESTATION_LEAVES` in `attestation-citation.ts`, keyed by `AttestationLeafName` (`value` / `signalKey` / `attestedAt`). Every leaf answers all THREE questions from one row: `groupKey` (the fold's identity), `counted` (the counting phrase) and `specific` (the drill-down's sentence). A fourth leaf is ONE new row and nothing compiles until all three are supplied. It was three parallel enumerations — a `FACT_PHRASES` entry, an `attestationGroupKey` switch, a `manualAttestationPhrase` switch — and a leaf half-added to one of them is what printed the ledger's own shape on a card. The two invariants below used to be prose in a comment; both are now structural, so do not re-express them as rules a reader has to find:
  - `counted` returns `Phrase`, NEVER `Phrase | null` — a `null` reaches `fallbackPhrase` and its ledger-shaped label, and the return type now forbids it.
  - `specificAtOne` is the ONE implementation of "drop the specifics above one row". A leaf gets that rule by using the builder, never by re-deriving `rows === 1` for itself.
- BOTH spellings hand the leaf the SAME `asserted`. A bare `manual.byKey.<signal>` passes the signal down; a bare `manual.attestations.N.signalKey` has no `=`, so `attestationCitation` substitutes the resolved signal — otherwise one spelling takes a different branch of the one template the dispatcher exists to share. Two spellings of one citation reaching the template differently is the divergence in its last hiding place.
- The TWO legal spellings are declared ONCE, in `attestation-citation.ts`: `MANUAL_BY_KEY_PREFIX` and `MANUAL_ATTESTATIONS_PREFIX`, plus the module-private `MANUAL_ATTESTATION_TEMPLATE_PREFIX` for the index-collapsed form. `snapshot-fact.ts` (attribution's read), `exit-criteria.ts` (`normalizeManualCitation`, and `attested` which builds each gate's declared path) and the formatter all import them. Never re-declare or hand-build either prefix — the pair once lived as `MANUAL_ATTESTATION_PREFIX` / `MANUAL_ATTESTATIONS_PREFIX` in two modules that import each other, one letter apart, with a third site building `manual.byKey.` by hand.
- ONE dispatcher decides what a citation asserts — `citationRendering` (`fact-format.ts`), with `formatCitedFact` and `formatCitedFacts` as thin wrappers over it. While the singular and plural paths were written separately the agreement between them was true only by test, and the routing is exactly where the divergence lived.
- The RAW citation is NEVER rewritten: the drill-down's `data-path` is what the judge wrote, and `buildEvidence` re-resolves that path verbatim against the snapshot. Attribution and wording are unified; the citation itself is evidence and stays as written.
- A CITED PATH IS UNTRUSTED INPUT — the judge writes it, so a segment may be `constructor`, `valueOf`, `toString` or `__proto__`, and the rule binds EVERY read of a judge-written key in this domain, not only the phrase lookup, AND IT BINDS THE WRITE THAT ASSEMBLES `manual.byKey` TOO: exactly three shapes are sanctioned, a `Map` read with `.get`, a `Record`/plain object read through `Object.hasOwn`, or — for an accumulator KEYED BY an untrusted string — a prototype-free `Object.create(null)`, NEVER a bare `in` and NEVER a bare `[key]` index. Both phrase vocabularies in `fact-phrases.ts` (`FACT_PHRASES` and `MANUAL_SIGNAL_CLAUSES`) are the `Map` half, so their lookup needs no guard at all: an object index reaches `Object.prototype`, and `constructor=4` handed a native function to `renderPhrase` and THREW out of both `formatCitedFact` and `formatCitedFacts` — a crashed `/phase`, because all three surfaces call them — while `toString=x` printed "[object Object]" and `manual.byKey.toString` read a function's source back to a planter. The `Object.hasOwn` half is four reads and there are no others: `attestationLeaf`'s read of `ATTESTATION_LEAVES` (the one taxonomy that deliberately stays a `Record`, because that read is already gated), `resolveSnapshotPath`'s per-segment walk and `resolveCitedFactSignals`'s dedupe (both `src/lib/phase-engine/assessment/snapshot-fact.ts`), and `signalFor` (`src/lib/phase-engine/fact-format.ts`). The `Object.create(null)` half is ONE site and it is the object those four reads WALK: `buildManualSignals` in `src/lib/phase-engine/signals/build-fact-snapshot.ts`, whose accumulator is keyed by `plant_signals.signal_key`. On a plain `{}` a row keyed `__proto__` created no own property, so it vanished from the snapshot with nothing failing, and one keyed `constructor` shadowed a prototype member on the object every later citation is resolved against. The WRITE also has a second gate now — `setManualSignalSchema` is a `z.enum` over `MANUAL_SIGNAL_KEYS` (`manual-signals.ts`), so no such key is storable through `setManualSignalAction` — but the rule holds at the assembly regardless: the reads were closed one by one while their source was left open, which is the same "some of its sites and not others" failure this section keeps recording. ## Tasks, Subtasks & Recurrence

→ [tasks](invariants/tasks.md) — `src/lib/tasks/**`, `src/app/(dashboard)/tasks/**`.

- ⚖ Nesting is ONE level, enforced in both directions: a subtask may not take children, and a task that already has children may not be demoted into one. Half the rule is no rule — refusing only the first is bypassed by parenting the other way round.
- ⚖ Completing every subtask does NOT complete the parent. There is deliberately no code that does it (#90); the absence is the ruling, not an oversight, and the UI says so out loud.
- ⚖ A subtask is a checklist item, not a task. Anything reporting a NUMBER of tasks applies `topLevelTasksOnly()` — `listTasks` and `getTaskCounts` share it, because the badges and the list under them must count one population (ruled on #370). Checklist progress is reported separately, never folded into `complete`.
- ⚖ A new subtask inherits its parent's assignee (#370). A default, not a lock — an explicit assignee wins and the subtask is reassignable. An unowned checklist item reaches no "My tasks" view and nobody is accountable for it.
- ⚖ The checklist is part of a recurring task's TEMPLATE: completing one mints the successor with EVERY item copied across, unticked — the ticked ones and the never-started ones under one rule (#370). Per-item carry-over state was rejected; a repeating task repeats whole.
- Copied children get explicit `created_at` stamps one millisecond apart. `listSubtasks` sorts by `created_at`, and one multi-row INSERT stamps every default with the same transaction timestamp, leaving checklist order to a random-UUID tiebreak.
- ⚖ Exactly ONE instance of a recurring series is open at a time, minted on completion — never by a cron. The guard runs BEFORE the successor insert, so a resurrected series gains neither a second open task nor a duplicate checklist.
- `completionEvent` is never copied to a successor: `meeting.evaluation.completed` is backed by a partial unique index, so copying it aborts the second instance's insert. Recurrence mints plain work; hooks stay with the generator.
- A completion is written FIRST and its successor second — the reverse of the usual durable-marker-last rule, deliberately. A successor with no completion leaves two open instances; a completion with no successor is repaired by reopening and re-completing.
- A task description is rich text on the SAME editor and sanitiser as a message body (T-021) — `normalizeTaskDescription` (`src/lib/tasks/descriptions.ts`) is the one write gate, and all FOUR writers go through it: `createTask`, `updateTask`, `importTaskTemplate`, `seedLaunchMilestones`. Enumerate the writers, do not name a plausible one.
- `description` means ONE thing on every row — the stored HTML — and a LIST row carries the readable summary BESIDE it, as `descriptionPreview`. Never one field with two meanings.
- The checklist catalog has TWO entrances and the prompt is never the only one: `/tasks/templates` is the standing route, linked from the `/tasks` header. It is a static segment beside `/tasks/[id]` — remove it and the URL resolves to a task with id `"templates"` and 500s, and `importTaskTemplateAction` becomes the not-yet-wired `"use server"` write Authentication forbids.
- ⚖ A phase change PROMPTS, it never creates (T-020). `handlePhaseChangedForTemplatePrompt` is registered on `phase.changed` and writes NOTHING; the absence is the ruling. Twenty tasks a planter did not ask for is the surprise the feature exists to avoid.
- The prompt is DERIVED, never stored: the latest `phase_transitions` row with `kind = 'transition'` plus the code-defined catalog. A `kind = 'initial_declaration'` row is not a move and prompts nothing.
- ⚖ The one stored thing is the ANSWER, and it is a ROW — `phase_prompt_answers`, one per transition, unique on `transition_id` (migration 0037, ruled 2026-08-10; re-stamped from 0035 on 2026-08-12). It re-arms the prompt by itself: the next move is a different id with no row against it. `PHASE_TEMPLATE_PROMPT_COOKIE` survives as a fast path only and may only ever suppress a prompt the row suppresses too — never restore one. That is ENFORCED ON BOTH ANSWERS, not merely intended: only a press holding a claim it KEEPS mints the cookie, and BOTH decision functions carry the split — `decidePhaseTemplateImportOutcome` for Import and `decidePhaseTemplateDismissOutcome` for "Not now" each return a `fastPathTransitionId` distinct from `answeredTransitionId`, which only says the route changed. An `already_answered` press mints nothing, whichever button it was: it found a concurrent press's claim, and an ACCEPT's claim whose import wrote nothing is released, which would otherwise leave a year-long cookie hiding a prompt the row says is unanswered. A decline can lose that race too, which is why `declinePhaseTemplatePrompt` reports `declined` vs `already_answered` instead of an id that cannot tell them apart.
- ⚖ Accepting is IDEMPOTENT per transition, on any device: `acceptPhaseTemplatePrompt` claims that row with `ON CONFLICT DO NOTHING` BEFORE its first import and runs only if the claim returned a row, so a repeat reports `already_answered` and writes nothing. Claim-first inverts the marker-last rule deliberately — the import it guards is not redo-safe.
- The claim happens AFTER the requested keys are filtered against the live prompt, never before: a forged key list must buy nothing, and spending the planter's one answer is something.
- Accepting dates the checklist from the TRANSITION instant, never from the press (`importedAt: transition.createdAt`), and the keys are re-filtered against a freshly derived prompt so a forged key imports nothing.
- A claim whose import wrote NOTHING is released, so the prompt returns; a claim whose import got part-way is KEPT, because re-offering a checklist already in the list is how a planter imports it twice. The remainder stays reachable at `/tasks/templates`.
- ⚖ The answer belongs to the PLANT, not to the planter (ruled 2026-08-12 on PR #393). `unique (transition_id)` is keyed by the transition alone and `/tasks` has no role gate, so ANY church member who opens it first answers that stage change **for everyone, on every device** — including pressing "Not now" on the planter's behalf. A deliberate consequence of the 2026-08-10 ruling, not an oversight; per-person answers need a wider key and a new ruling.
- Because that answer is the PLANT's and cannot be un-answered, "Not now" carries a STALENESS GUARD (#313): the panel posts the `transitionId` it was rendered for in a hidden input, and `declinePhaseTemplatePrompt` writes no row and returns `null` unless that id EQUALS the plant's current transition. Without it, a prompt left open while the plant moved on declined the stage change the presser never saw. The id is a GUARD, never an AIM — it can only match the row the function would have chosen anyway, so the deliberate "the dismiss action chooses no transition" posture holds and the worst a forged value buys is a no-op, reported as `DISMISS_FAILED_MESSAGE`. Accept never needed this: it re-filters the posted keys against a freshly derived prompt, so a stale key list collapses to `null`.
- ⚖ Import REFUSES an empty selection (ruled 2026-08-12): the button disables while no checklist is ticked, says why beside itself, and "Not now" stays live as the only way out. Unticking everything and pressing Import was otherwise a silent no-op — and it made the untick copy false, because the checklists came straight back.

React 19 restores an uncontrolled form to its `defaultChecked` state after a `<form action>` action settles and fires NO `change`, so besides the bubbled `change` handler a `useEffect` keyed on BOTH outcomes re-reads `tickedTemplateCount(form)` after every settle; both writers call that one function. Without it a settled `nothing` / `failed` (import) or `failed` (dismiss) — the three outcomes that leave the panel mounted — left a DISABLED Import above visibly ticked boxes, and a retry imported the restored ticks the planter had unticked. It is the DOM-subscription case, not `useEffect` data sync: nothing there is server data and no prop is mirrored.
- A part-way import RETURNS `partial`, it does not throw, and its receipt is SERVER markup driven by a flash cookie — never client state in the prompt's island. The claim is kept, so the transition is answered and the next render of `/tasks` has no prompt and no island in it; "just revalidate nothing" cannot save it, because setting a cookie in a Server Action re-renders the route by itself (`.next-docs/.../cookies.mdx`) and answering always sets one. Two earlier attempts died here — `revalidatePath` only, then `revalidation: "none"` — the second verified in a browser as 16 of 22 tasks created, the stage change spent, and no message anywhere. `decidePhaseTemplateImportOutcome` returns a `receipt`; `importPhaseTemplatesAction` writes it to `PHASE_TEMPLATE_RECEIPT_COOKIE` BEFORE the answer cookie; `PhaseTemplatePrompt` decodes it in the branch where there is NO prompt — the branch that used to `return null` — while a live prompt still wins over a stale receipt; `ClearReceiptCookie` spends it once read. The decoder never throws — `/tasks` has no error boundary and that cookie is the browser's to forge.
- The receipt CARRIES THE TRANSITION IT REPORTS ON (`PhaseTemplatePartialReceipt.transitionId`) and is drawn for no other. "A live prompt wins" and "the flash is spent by being shown" leave a hole together: a receipt beaten by a new prompt is never shown, so it is never spent, and the render after the planter answers THAT prompt cleanly would announce "the remaining checklists were not created" in a destructive `role="alert"` about a press where every clause is false. A render cannot clear a cookie (`cookies().set` is Server-Action-only), so the id travels in the value — refused on decode when absent or empty, which also retires every pre-id cookie — and `receiptForTransition` matches it against the render's own latest transition. That id comes from `readPhaseTemplatePrompt`, the ONE composition of "read the latest transition, build the prompt", so both come out of a single query and the plant cannot move between them.

Three independent conditionals stacked two live regions once an import failure and a decline failure were both on record, because each `useActionState` hook keeps its last result forever. ## Migrations

- RESERVING AN `idx` DOES NOT RESERVE AN ORDER — `when` is what decides. `drizzle-kit migrate` applies a migration only while the ledger's MAXIMUM `created_at` is strictly less than that migration's `when`, so a sibling holding a lower `when` on another branch is SILENTLY SKIPPED once the higher one lands anywhere: success, exit 0, nothing applied. A migration that raises its `when` above a reserved sibling therefore owes that sibling a FORWARD reconcile in its own header — name it by tag and branch, and state that it must be re-stamped above this `when` (and renumbered) before it merges. Never hand-rename a freshly GENERATED migration: `drizzle-kit generate` uses max(idx)+1 and numbers it correctly on its own. Worked example: `0036_association_subject_and_notification_anchor.sql` → `0035_phase_prompt_answers` on `feature/U313-WS1`.
- ⚖ A RENUMBERED migration ships with an OPERATOR RECONCILE step or it does not ship (#304 round 8, ruled 2026-08-10). `drizzle-kit migrate` decides what to apply by comparing each journal `when` against the ledger's MAXIMUM `created_at` — never by asking whether THIS migration's own row is present — so every database that already applied the OLD number is invisible to it: the columns are there, the new `when` is higher, the DDL re-runs and the apply aborts on `column ... already exists`. The renumbered file's header must therefore carry the reconcile: how to detect that state (the `information_schema.columns` probe plus `select max(created_at) from drizzle.__drizzle_migrations`) and both exits — record the apply that already happened on a database with rows worth keeping, or run the rollback block and re-apply on a scratch one. Prove either from `information_schema.columns`; the CLI exits 0 for "skipped" and for "applied" alike. Worked example: `src/db/migrations/0036_association_subject_and_notification_anchor.sql`.

## Dev Seeds

Why and how: [`contracts/db.md`](contracts/db.md) → The dev-seed wipe. Applies to
`scripts/seed-dev-db.ts` and anything that inserts a `churches` row.

- `pnpm db:seed` deletes ALL users and ALL churches unscoped — the fixture is the whole database, not the rows the script created. Run it against your own or a throwaway database ONLY; on the shared `development` branch it takes the alpha-cohort logins, the marketing fixture and every hand-registered plant.
- The wipe REFUSES to run on a database holding an alpha-cohort sentinel account unless `--allow-protected-db` is passed (`src/lib/dev-seed/protected-database.ts`, ruled 2026-08-09). Detection is POSITIVE — sentinel rows, never "does this connection string look like development", which fails open. Passing the override on the shared database is a deliberate, destructive act, not a way past a nagging prompt.
- The wipe ORDER is derived at runtime from `pg_constraint` by `planWipe()`. Never re-introduce a hand-kept table list — the derivation is what makes a new table join the wipe on its own.
- `wiki_articles` and `wiki_sections` are `PROTECTED_TABLES`: never deleted AND never walked through, so nothing downstream of them is dragged in either. The corpus is migrated content no script rebuilds (#317).
- A protected row pointing at a table the wipe deletes (a church-scoped wiki article) ABORTS the whole seed before its first DELETE — `assertProtectedTablesAreSafe()`. Stop and re-point by hand; never widen the wipe to cover it.
- Every script that inserts a `churches` row stamps `onboarding_completed_at` with `now()` in that same INSERT — an unstamped seeded church puts its planter in the onboarding wizard instead of the dashboard. Pinned by `src/lib/onboarding/seeded-churches.test.ts`.
- EVERY seed mode asks the sentinel BEFORE it writes, and no in-repo constant is a working password on a protected database (#304 round 8, ruled 2026-08-10). `--oversight-orgs-only` deletes nothing and was therefore called "the one mode that is safe on the shared development database" in three places; it INSERTS a `sending_church_admin` login, so it was a repo-readable credential on whatever database it last ran against. It now asks `decideSeedAccounts` — the same `matchProtectedAccounts` query the wipe asks — refuses a protected database with NO override, and takes its password from `SEED_ADMIN_PASSWORD` with no default (unset is a refusal). Additive is not a synonym for safe; the question a destructive-check answers is "which database is this", and writing a login needs that answer too.
- A seed mode that ANNOUNCES a password must have SET it: `--oversight-orgs-only` upserts both oversight admins (`onConflictDoUpdate` on `users.email`, setting `password_hash`, role and the org FKs), never `onConflictDoNothing` (#304). Re-keying is licensed ONLY by `decideSeedAccounts` having already refused, with no override, on any database holding a sentinel.
- ⚖ A credential removed from the repo needs a ROUTE, or the fixture it opens becomes unreachable: `SEED_ADMIN_PASSWORD` is recorded in `.env.local` — gitignored, machine-local, loaded by `seed-dev-db.ts`, and read by a verifier BEFORE seeding rather than re-chosen (#304, ruled 2026-08-11). Passing it inline still writes a real credential and prints `unrecordedPasswordNotice`.
- The mode's credential write is keyed on the ADDRESS (`OVERSIGHT_ADMIN_EMAILS` in `src/lib/dev-seed/oversight-admin-upsert.ts`), never on the role — a role is not unique by construction. The statement and the address resolution live in that module, not inline in the script, so `seed-account-writes.test.ts` asserts the emitted SQL and calls the resolver instead of grepping the script.
- The sentinel probe proves ONE thing: the three `PROTECTED_ACCOUNTS` addresses are absent. It does NOT prove every account on a database is fixture, so the re-key's only guarantee is "it cannot seize a sentinel". Widening the fixed oversight pair, or the mode's reach, needs a ruling and not just the probe.
- The FULL seed gives those two admins `password123` like every other row, but no shared database is ever full-seeded — so wherever a credential is printed, name the MODE that set it. "Password for all users" over an address a preview cannot open is how a verifier concludes the login form is broken.
- The seed owns exactly ONE `sending_networks` row and ONE `sending_churches` row, on PINNED uuids inserted with `onConflictDoNothing`. They exist so a `sending_church_admin` has an org to belong to: before #304 round 6 the dev database held NO account with that role, so every screen it reaches was unreachable by a real login and could not be browser-validated at all. They stay OUTSIDE the wipe (`planWipe` reaches neither table) — deleting them would take org rows the script never created — and the pinned ids make that free, since a re-seed re-inserts the same keys instead of accumulating a second copy.

## Date & Time Rendering

→ [dates-times](invariants/dates-times.md) — anything rendering or parsing a date.

- Never format a `Date` without a pinned `timeZone` — format through `src/lib/datetime.ts` (`APP_TIME_ZONE`, UTC). `Intl`/`toLocale*`/date-fns follow the runtime's zone, so SSR and hydrated markup differ (React #418).
- A meeting's `datetime` is a wall clock, not a zoned instant: `meetingDatetimeSchema` with `parseDateTimeLocalValue()`/`toDateTimeLocalValue()`, never `z.coerce.date()`.
- There is no per-user or per-church timezone column. Adding one means changing `APP_TIME_ZONE` and back-filling, never re-introducing runtime-local formatting.

## Client/Server Data Synchronization

Conventions and examples: [`contracts/data-patterns.md`](contracts/data-patterns.md).

- NEVER store server data in `useState` (it goes stale the moment the server revalidates) and NEVER sync data with `useEffect` — server data flows through props from server components.
- Use `useOptimistic` for instant feedback; the server action calls `refresh()` from `next/cache` to reconcile, not the client calling `router.refresh()`. Example: `ActivityTimelineClient`. Props-only is the other shape — no local state at all (`TagPicker`).
- Legitimate client state is UI state only — pagination cursors, drag-and-drop, open/closed (`PipelineView`).

## Design Tokens — Contrast

Applies to `src/app/globals.css` and every stylesheet under `src/app/`; pinned by `src/app/text-contrast.test.ts`.

- Text contrast is a property of the TOKEN, not of a screen: `--muted-foreground` must clear WCAG AA 4.5:1 on ALL EIGHT surfaces it lands on (`--background`, `--card`, `--popover`, `--muted`, `--secondary`, `--accent`, `--sidebar`, `--sidebar-accent`) in both themes, and a failure is remedied by darkening the token in `src/app/globals.css` — NEVER with a per-component color override, which is the workaround #341 was filed to replace.
- ⚖ WCAG AA (4.5:1) is the standard that BINDS `--muted-foreground`; APCA is advisory and is never a reason to lighten it (ruled 2026-08-10, #386 — the token sits at APCA Lc 68.2 on `--muted`, under the Lc 75 body-text guidance, and ships anyway).
- The cost that darkening carries is INLINE-LINK SEPARATION, and the two move in opposite directions: as `--muted-foreground` darkens it converges on `--primary`, so a link inside muted prose drops under the 3:1 WCAG SC 1.4.1 asks when colour is the only cue — 3.61:1 at the pre-#341 L 0.556, 2.85:1 at the shipped L 0.5, 2.06:1 in the dark theme.
- ⚖ That cost is paid in CSS, never by capping the token's lightness (ruled 2026-08-10, PR #387): `p a[href]` carries a permanent underline at REST — hover is not a rest state. Never delete that rule and never put `no-underline` on a link inside prose — either one puts SC 1.4.1 back at the mercy of wherever the token's L happens to sit.
- The underline rule is NOT paid once, and believing it is shipped the bug: it lives in `@layer base` of `src/app/globals.css`, which is the WEAKEST place in the cascade, and an UNLAYERED normal declaration beats a layered one at ANY specificity. Every unlayered stylesheet under `src/app/` that touches `text-decoration` on a bare `a` selector therefore owes its own `<scope> p a[href] { text-decoration-line: underline; text-underline-offset: 4px }` — `src/app/(marketing)/marketing.css` does, because `.marketing a { text-decoration: none }` had silently deleted the cue across the whole marketing route group (/terms and /privacy shipped four links at 1.36:1, worse than the 2.85:1 /login case). Fix a conflict of this shape on the sheet that caused it; NEVER with `!important` in `globals.css`.
- The diagnostic for that failure is an asymmetry in computed style: `text-underline-offset: 4px` present (only the base rule sets it) while `text-decoration-line` is `none`. A grep of `globals.css` cannot see it and neither can a grep for `no-underline` — only the browser or the unlayered-stylesheet guard in `src/app/text-contrast.test.ts` can.
- Accepted residual: `--ring` is 2.4:1 on `--background` in the light theme and ~1.5:1 once `focus-visible:ring-ring/50` composites, so focus indicators fail WCAG 2.2 SC 1.4.11 (3:1); Lighthouse cannot see it and scores 100 anyway. Retired by #385.
