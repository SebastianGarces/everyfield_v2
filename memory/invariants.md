# Invariants

**Every rule is stated below, one line each — these lines ARE the rules**, not a table of contents for them. Read only this file and you have still seen every rule.

Audited 2026-08-19: rules the source, schema, or tests already answer were removed — read the code first.

Rules bind at two strengths (`ops/process.md` → The loop, step 3):

- An **untagged line is an invariant** — a mechanical or security fact. Never break it; a change that needs to is wrong.
- A line tagged **⚖ is a ruling** — a dated product decision. Never break it *silently*: build to it, and if it no longer fits, rule on it per `ops/process.md` → The loop, step 2 (*Decide, don't ask*) and record why. A new ruling changes it; nothing else does.
- A line starting **Accepted residual** is a known gap, carried deliberately until the named condition retires it.

Some sections link `invariants/<domain>.md` for the why, the pattern and the worked examples. Read the domain file for what you are touching; read all of them as the security lens.

## Transactions / Atomicity

→ [transactions-atomicity](invariants/transactions-atomicity.md) — any DB write path.

- `db.transaction()` throws at runtime — neon-http has no interactive transactions. Never call it.
- Where the earlier steps of a marker-last sequence are NOT redo-safe, the marker becomes a CLAIM written FIRST (`ON CONFLICT DO NOTHING` on a unique index), and the non-idempotent work is gated on the claim's rowcount.
- In a batch the compare-and-set goes FIRST and the dependent write's `WHERE` re-asserts what the claim set — an empty `returning()` is not an error and rolls nothing back.
- A compare-and-set serialises only same-row writers; a predicate about another table is a snapshot read. To compete for a row elsewhere, `SELECT … FOR UPDATE` it as statement ONE and gate on the write's rowcount.
- In a `WITH` chain a `FOR UPDATE` snapshot CTE must be a DEPENDENCY of the write (`update … from current c`), never a sibling only the journal joins: pulled lazily it reads nothing, and the history row is lost.
- A migration that adds an arbiter index goes FIRST: `ON CONFLICT (…) WHERE …` against a database lacking it is SQLSTATE 42P10 on EVERY call, and nothing here applies migrations on deploy — code-first is the default unless an operator runs `pnpm db:migrate`.
- Accepted residual: `createHouseholdWithHead`'s two statements take separate READ COMMITTED snapshots, so a person soft-deleted between them commits an orphan household.
- `isUniqueViolation` (`@/db/errors`) matches on the `constraint` FIELD and nothing else. The `message.includes(<index name>)` fallback was DELETED (#323): Postgres puts the offending VALUE into some unique-violation messages, so a crafted row made somebody else's violation read as our index doing its job — and every caller swallows that as a benign race. Both shapes the drivers really raise populate the field.

## Multi-Tenancy

→ [multi-tenancy](invariants/multi-tenancy.md) — invitations, associations, onboarding.

- All feature data carries `church_id`; `church_id = null` means global content (wiki articles).
- Tenant isolation is enforced in the application layer; there is no RLS behind you.
- ⚖ An existing account MAY be targeted, but EVERY refusal reachable after the address resolves to a target is the ONE message `ACCOUNT_NOT_INVITABLE_MESSAGE`. The property is positional: anything downstream of `resolveInvitationTarget` speaks about a STRANGER.
- ⚖ No invitation that cannot be answered, for every role: each TYPE that can name an existing account has an in-app surface where that role answers it AND leaves the association.
- ⚖ One inviting org may address ONE email at most `INVITES_PER_INVITEE_PER_WINDOW` (3) times per `INVITATION_EXPIRY_DAYS`, counting EVERY status. The cap runs BEFORE target resolution and covers open invitations.
- ⚖ …and it RESETS AFTER A SEVER: both count queries drop every invitation older than that org's most recent `association_events` row about the same subject. A decline writes no event, so that loop stays capped.
- ⚖ The create-invitation success notice shows ONE neutral message for both kinds and never says whether an account exists.
- ⚖ The rule covers the WHOLE `/oversight/invitations` page, notice AND pending list: nothing derived from either target column reaches the client, and no admin surface renders a `/register?invitation=` link.
- ⚖ The rule is TRANSITIVE and `type` is target-derived, so a caption off `invitation.type` flips for an address holding an account of the other kind. `InvitationListRow` carries five fields, built by `toInvitationListRow`.
- ⚖ The rule reaches `/register` and BOTH readers of the row, and the two verbs have DIFFERENT indistinguishable sets: the GET for {targeted, answered, nonexistent}, the POST for those plus an open row submitted with a NON-matching address. ONE predicate decides.
- ⚖ The anonymous `/register` POST returns NO per-row message: a wrong-address submit falls through to the ordinary sign-up exactly as an unknown id does. One decision is made once and read by every later branch.
- Accepted residual: an OPEN row stays distinguishable at `/register` — the GET renders the redeeming form with a pre-filled `readOnly` address (never `disabled`, which submits nothing), and the matching POST redeems. Retired by invite-at-registration.
- ⚖ `association_events` names a SUBJECT, not a plant (0036): `subject_type` ∈ {church, sending_church}, one nullable FK per kind, a CHECK that exactly one is set. `acceptInvitationAs` has ONE batch shape, `[lock, claim, sharing, association, audit]`; `requireAssociationPair` decides which ids a type implies.
- ⚖ A notification is anchored to a CHURCH or to an ORG (`anchor_type`, `anchor_org_id`, CHECK exactly-one) — ONE table, never a parallel org table, and neither tenancy coalesces with the other.
- An oversight audience arm is its org's FK AND the rest of the exactly-one-tenancy rule (`church_id` null, every other oversight FK null) — the SQL half of `oversightOrgOf`. Never the FK alone: that admits a row with a competing claim on another tenancy. The other columns come off `OVERSIGHT_ADMIN_ROWS`, so a third org kind tightens every arm.
- ⚖ A `users` row an oversight FK reached whose OWN TENANCY is not that org is a DATA DEFECT, never a recipient: the audience PARTITIONS them (`OversightAudience`), so `fanOutTo` loops `recipients` alone and logs the rest. The exclusion is in TypeScript, not the `WHERE`, to be COUNTED; `oversightReachCondition` is that probe, never an audience.
- That log names the row's OWN tenancy columns (`names`), never the org it administers: a row only reaches that branch by naming more than one tenancy, and such a row administers nothing — so an "administers" field could only ever print null, which is a count an operator cannot act on.
- ⚖ A pending invitation carries a "Resend email" action so a failed or missed send is recoverable. NOTHING is persisted about delivery, because provider acceptance is not a delivery receipt.
- ⚖ After a successful resend the button is DISABLED for the rest of that 60s bucket (`RESEND_DEDUPE_WINDOW_MS`) and counts it down. ONE arithmetic feeds both the provider idempotency-key suffix and the countdown, and only DURATIONS cross to the browser.
- Accepted residual — ⚖ that cooldown is PER CLIENT SESSION: it lives in `useActionState`, so a reload or a second tab mounts with none. Retired only by reversing the no-persistence ruling.
- ⚖ AND THE ADMIN LINK DOES NOT COME BACK: the create result carries `{ inviteeEmail, emailSent }` and no path, and no notice or row renders a link or Copy control. The rule reaches the refusal copy too.
- ⚖ THREE SEVERS, one per side of the two associations. None calls the bare `disassociate*` primitives, which stay out of every `"use server"` module — a sever's FK write asserts the org it severs.
- ⚖ A sever ships only where the audit table can hold its subject: a type-to-confirm, a notification AND an `association_events` row are required. A sending church can only be severed FROM a network.
- ⚖ AN OVERSIGHT ACCOUNT'S FEED IS SCOPED TO ITS ORG, NOT TO A CHURCH (N-027, #308): `notificationViewer` asks the tenancy FIRST, and `oversightScopedWhere` is ONE recipient predicate ANDed over a THREE-arm OR — but only TWO of the arms are bounded by an ANCHOR. Arm 1 is `church_id IN (…)` over the plants that are in the org's portfolio AND have `share_activity_with_oversight` on — a SUBQUERY, evaluated at read time, never an id list a caller assembled. Arm 3 is `anchor_org_id = org.id`, which retires the write-only residual on org-anchored rows. Arm 2 is a TYPE test alone — `type IN OVERSIGHT_SHARING_EXEMPT_TYPES`, read off the constant `enqueue`'s gate reads — bounded by nothing but the recipient. Every user-facing path goes through `feedScopedWhere` — the list, the badge, the cold-start probe, the by-id read AND both mark-read UPDATEs — so a plant that has not opted in is unreachable by direct id and unmarkable, not merely unlisted.
- Accepted residual (#527, from #526's review): because arm 2 names no anchor, an exempt milestone stays visible to its recipient after the plant leaves the portfolio AND after that recipient is re-seated elsewhere. It is bounded by the RECIPIENT, so it never widens to another account — the row is the reader's own record of a relationship they were part of, which is why the arm exists. Closing it needs `anchor_org_id` stamped on exempt milestones at write time, and backfilled: a migration, deliberately out of scope.
- Accepted residual: a sending-church-subject `association_events` row is WRITE-ONLY, because the one reader filters on `church_id`. Retired by the first surface that shows it, widening the query by SUBJECT.
- ⚖ SEAT invitations (`user_invitations`, #495) are the SAME rulings on a second table, never a second copy: `INVITATION_EXPIRY_DAYS`, `INVITES_PER_INVITEE_PER_WINDOW`, `RESEND_DEDUPE_WINDOW_MS`, `ACCOUNT_NOT_INVITABLE_MESSAGE` and `resendRefusalMessage` are IMPORTED from `invitations/core.ts` and `invitations/resend*.ts`, and `/settings/team` renders the org surface's own `InvitationsList` given its two actions.
- ⚖ …and they INVERT only the first clause, FOR THE `seat` KIND ONLY: a seat invitation is REGISTER-ONLY, so an address that already holds an account of ANY kind is refused with `ACCOUNT_NOT_INVITABLE_MESSAGE`. The positional rule is unchanged — the authority check, the email parse, the duplicate check and the cap all run ABOVE the `users` lookup, and nothing below it composes a sentence.
- ⚖ A `coach` INVITATION KEEPS THE EXISTING-ACCOUNT PATH and is NEVER refused with that message (AS-009, ruling 185 (5), #496): a seat invitation would MOVE an account between tenancies, a coach one only ADDS a `coach_assignments` row. ONE predicate decides both — `inviteeRefusalFor(kind, existingAccount)` off `INVITATION_KIND_RULES`, which also names each kind's create verb (`seat.invitation.manage` / `coach.assignment.manage`, both ADMIN_PLUS on a plant).
- ⚖ …so the invitee needs a surface, and it is `/coach-invitation`, which forks on the VIEWER'S SESSION and never on the invitee: signed in it offers Accept, signed out it hands on to `/register` with the same token. `oursFilter` therefore covers BOTH kinds — a kind predicate there would make every coach invitation invisible to the plant that sent it and un-revokable by anyone.
- ⚖ A COACH'S GRANT IS ONE `coach_assignments` ROW AND NOTHING ELSE: no tenancy FK, no seat, no `persons` row. It is written by `assignCoachOnAcceptStatement`, an `INSERT … SELECT` batched AFTER the claim whose `WHERE` re-asserts `status='accepted'` and whose coach and plant are READ OUT OF the invitation row. `ON CONFLICT DO UPDATE SET status='active'` because the unique index is total, not partial on status, so a re-accept must revive an ended assignment rather than 500.
- ⚖ `coach.invitation.answer` carries NO seat set and NO tenancy (`seats: null, tenancy: "any"`): who may answer is decided by the TOKEN and the address it is bound to, not by standing, and any narrowing refuses the seatless coach the invitation is most often for. A re-invite of an ACTIVE coach is refused above the lookup with `ALREADY_COACHING_MESSAGE`, scoped to the caller's own roster — which the caller already reads by name on the same screen, so it states nothing new.
- ⚖ THE SEAT TOKEN IS A SECRET, NOT AN ID: `token_hash` holds sha256 of a 32-byte token that exists only in transit, so a resend cannot repeat a link and MINTS a new one. `?invitation=` carries either kind; the seat lookup is a point read on the digest, which a uuid never matches, so the two never collide.
- ⚖ …so a seat resend's PROVIDER KEY is its ROTATION, never the 60s bucket: two resends in one bucket share a key, the provider swallows the second, and the row is left holding the digest of a link nobody has. A refused resend restores the previous digest, and `describeSeatInvitationForRegistration` throws rather than returning null on a database failure — a null there registers the invitee as a cold planter at an address AS-010 will not re-invite.
- ⚖ A seat invitation grants its tenancy FK and its seat AT REGISTRATION, in the SAME `db.batch` as the users insert, the person link and the claim — which is what keeps "outside registration a seat is granted in exactly one place" true. `userChurchId` is the field that distinguishes it from an invited planter, whose link is still the compare-and-set (ruling 408-4B).
- ⚖ THE SAME SEAT INVITATION SERVES ALL THREE TENANCIES (AS-005/AS-007, #500) — the table already admitted the two org FKs, so the org side WIDENED `seat.invitation.manage` from `tenancy: "plant"` to `tenancy: "tenancy"` rather than declaring a second verb. `tenancy` is the union of "a plant that exists" and "an oversight org" and is NOT `any`: it refuses the registered Owner whose plant does not exist yet, who holds a seat and names nothing for the verb to act on.
- ⚖ …and WHICH tenancy is ONE value, `SeatTenancy` from `tenancyOf` (`@/lib/auth/tenancy`), never three nullable FKs threaded separately. `oversightOrgOf` is now that resolution with `church` removed, so the two cannot disagree; `tenancyColumns` is the inverse and is SPREAD by both writers (the invitation insert, the users insert at registration), which is what satisfies `user_invitations_tenancy_check` by construction. `user_invitations`' projection IS `TenancyFields`, so an invitation row resolves through the same function a session does.
- ⚖ THE INVITING TENANCY IS NEVER A CLIENT FIELD. `UserInvitationRequest` carries an address and a seat and nothing else; the target is the ACTOR'S own, resolved by `invitingTenancy`. That — and not a validator — is what makes "an org invitation never targets a plant" true of the wire.
- ⚖ AN ORG SEAT WRITES NO `persons` ROW (ruling 185 (9)): AS-013's match-or-create is a PLANT's directory question, so both the lookup in `register/actions.ts` and `accountPersonLinkStatements` in the planner sit behind `tenancy.type === "church"`. An org Member is an account, never a person record inside a plant.
- ⚖ AN ORG MEMBER READS EVERYTHING ITS OWNER READS AND CHANGES NOTHING (AS-007, ruling 185 (3)). The reach never branches on the seat — `getAccessibleChurchIds` resolves the org from the FK alone — so parity is structural. The REFUSALS are the capability table's (`org.invitation.manage`, `org.association.sever`, `org.association.leave`, `seat.manage`, `org.settings` are all Owner-only), and every surface that renders one of those verbs now ASKS that table: `/oversight/invitations` gates its create form and the row's resend/revoke on `canManageInvitations`, `PlantDetail` takes `canSever`, and `/settings/association` asks `isOrgOwner` rather than the sending-church FK alone. A control beside an action guaranteed to refuse it is the visible half of a permission drift.
- ⚖ …and that includes the ASSOCIATION INVITATION LIST: `readableOrgOf` scopes it by the org FK ALONE, and `invitingOrgOf` — the predicate the revoke and the resend carry — is that same derivation AND-ed with `isOrgOwner`. The 2026-08-04 rule the once-shared predicate protected (never show a row whose Revoke is refused) now lives on the render side instead: `/oversight/invitations` draws both controls only for `org.invitation.manage`. A read scope narrower than the surface is a page that promises a history and prints an empty list for ever.
- ⚖ NO EMPTY STATE OFFERS AN INVITE ITS READER CANNOT SEND — the oversight index, `PlantsDirectory` and `SendingChurchesRoster` all gate their "Invite a …" call to action on `org.invitation.manage`. The emptiest screen in the product is the one where a refused control is the ONLY thing on it.
- ⚖ A SEAT REMOVAL'S CASCADE IS THE PLANT'S, NOT EVERY TENANCY'S. `removeSeat` batches sessions-delete + marker for an org and sessions-delete + `plantRemovalEffects` + marker for a plant: a sending church and a network have no `tasks` and no `ministry_teams`, so those writes are meaningless rather than empty there. The marker is LAST in both, which is what redo safety rests on, and `REMOVAL_CONSEQUENCES` in the confirmation dialog says exactly what its own batch does.
- ⚖ `/settings/team` is ONE screen for all three tenancies, and only the COACH sections are plant-gated — `coach.assignment.manage` stays `tenancy: "plant"`, so an org cannot create a coach invitation and `listPlantCoaches` refuses one outright. A parallel org team screen would be this file with one word swapped and would drift on the first change to either.

## Hierarchical Access Control

→ [hierarchical-access](invariants/hierarchical-access.md) — every oversight surface.

- Oversight users see AGGREGATE metrics only, never individual person records.
- Call `canAccessFeatureData(user, churchId, feature)` before returning feature data; the six `share_*` toggles default false and gate what oversight may PULL.
- ⚖ PUSH is far narrower: an oversight recipient gets ONLY the daily digest and three milestone events, and `enqueue` refuses every granular category for them, gated on `share_activity_with_oversight`.
- That toggle gates PUSH only and the consent copy may not claim more — plant health (name, phase, launch countdown, health) returns with NO privacy gate.
- ⚖ A refused category is never OFFERED either: the settings screen and the preference action both derive from `OVERSIGHT_ELIGIBLE_CATEGORIES`, never a second list.
- ⚖ THE SIX PULL TOGGLES ARE ONE ORDERED LIST WITH THEIR COPY, `SHARING_PULL_TOGGLES` (`@/lib/sharing/toggles`, CS-011) — the panel renders it, the write action validates against it and `oversight/sections.test.ts` asks it which keys are pull toggles. A seventh `share_*` column widens `PrivacyFeatureKey` and fails the BUILD there until it has a row. The write flips the column `privacyColumnFor` names, so the column written and the column `canAccessFeatureData` reads back cannot come apart.
- ⚖ TURNING A SHARING TOGGLE OFF ANNOUNCES IT, COARSELY, TO EVERY OVERSEEING ORG (CS-012, ruled §187 2026-08-15): `oversight.milestone.sharing_changed`, wording that names no toggle, one notice per PLANT per ORG per DAY so the count of notices cannot reassemble the per-toggle detail the ruling forbids. Both halves of that occurrence are load-bearing — `composeMilestone` keys on the ANCHOR, which here is the org, so a day alone gives every plant under one org the same key and the second plant to change anything is swallowed. Turning one ON sends nothing, and neither does a write that lands on the value already there (`setSharingToggle` reports `changed` from its own `setWhere`).
- ⚖ …and it is ORG-ANCHORED and CONSENT-EXEMPT, both structural rather than stylistic: arm 1 of `oversightScopedWhere` would hide a church-anchored row from an org the plant just stopped sharing with, and gating the notice on the toggle being changed would let the push toggle silence its own announcement.
- ⚖ Its ruled presentation is SHOWN-AND-LABELLED, not hidden: the five rows stay visible with a "Not sent to you" token and inert switches, and the reason is said once, visibly.
- ⚖ The consent copy NAMES EVERY consent-exempt type in one sentence with the reason — FOUR since #619, because closing a toggle is itself something the org hears about. The reversibility bullet sits ABOVE it; pin it by a map keyed on the exempt-type list, never a hand-written count, so a fifth exemption fails CI until every surface names it.
- ⚖ AN INVITE-ORIGIN PLANT STARTS SHARING EVERYTHING AND A SELF-STARTED ONE STARTS SHARING NOTHING (CS-013, ruled 2026-08-15 §187, #620) — the column defaults stay FALSE and the ON write is the ACCEPTANCE's, `sharingDefaultsStatement` (`@/lib/privacy/sharing-defaults`) batched inside `acceptInvitationAs`. Rationale is #193: the sending org pays per plant, and paying while seeing nothing is the failure mode. ONE statement serves BOTH acceptance paths because an invited planter's registration hands off to the same `acceptInvitationAs` (`redeemRegistrationInvitation`); writing it in the REGISTER batch instead was rejected by name — that redemption is best-effort and never throws, so a failed one would leave a plant sharing everything with an org it had not joined and could still DECLINE.
- …and it is TOTAL, never conditional, which is what keeps that batch at ONE shape: the statement JOINS `churches` on the invitation's own `target_church_id`, NULL for `sending_church_to_network`, so the type with no plant joins no row and writes nothing — no ternary for a later edit to make reachable. It re-asserts `status = 'accepted'` for the reason every batched write here does: a zero-row write is a success, so a LOST claim would otherwise share a plant whose accept was refused.
- IT FIRES ONLY FOR A PLANT WITH BOTH OVERSIGHT FKs STILL NULL, which is why it is batched BEFORE the association write rather than after it — that is the last statement at which the plant's row still says who it belonged to when Accept was pressed. An accepted association does not block a later invitation and `unboundTargetSlot` lets an accept re-bind the org it already holds, so without the gate a re-invite from an org the plant already belongs to would reset toggles the planter had deliberately turned OFF. BOTH FKs, not the one the invitation names: `church_privacy_settings` is ONE row per church governing every org that reaches it, so a plant that already has an overseer has already made this decision.
- It is an `INSERT … SELECT … ON CONFLICT DO UPDATE`, not an UPDATE, because the privacy row is not guaranteed — `scripts/seed-dev-db.ts` creates churches without one — and a plain UPDATE would leave the ruling silently unapplied on exactly the plants nobody checks. Same reasoning, same shape as `ensureSharingRow` and `assignCoachOnAcceptStatement`. NO `returning()`: zero rows is the EXPECTED already-associated outcome, so a rowcount carries no signal a caller could act on.
- The written set is EVERY BOOLEAN COLUMN THE SCHEMA HAS, read off the table by `SHARING_TOGGLE_COLUMNS`. Never a list typed in a file: #62's wiki toggle is one column away, and a hand-kept array ships an invited plant sharing six of seven with no screen to say which. Drizzle additionally requires an insert-select's fields to mirror the table's column order, so the selection stays schema-keyed by construction.
- ⚖ …and the copy comes FIRST: `INVITE_ORIGIN_SHARING_CONSENT` renders ABOVE the accept control on both screens a plant can accept from, and it is in `OVERSIGHT_CONSENT_SURFACES` so every consent guard applies to it. On `/settings/association` it renders ONLY while the plant has no association, because that is exactly when the write fires and therefore when "starts you off sharing" is true.
- ⚖ AND IT PROMISES NO CONTROL THAT DOES NOT EXIST. The rule is the constraint, not the sentence: a draft reading "any part of it, or all of it" described a screen the planter did not have, so the copy was cut back to the one switch and the sever. #619 SHIPPED the panel — six pull switches and the push switch in the Church section — so the per-part promise is back in the copy, and it comes out again with the panel if the panel ever goes. It still names neither financials nor facilities (both flip on, both gate a section with no data model) and still states the ungated plant LISTING as a limit. `oversight.test.ts`'s hardcoded-prose denylist carries `/you can change/i` so the next PAGE-LOCAL control promise fails CI whatever the shared copy says.
- ⚖ A COACH'S READ IS UNGATED BY `share_*` AND IS OF THE PLANT'S OWN RECORDS (AS-008/AS-011, #496). The toggles gate what OVERSIGHT may pull; a coach's consent is the assignment the plant wrote by name, so `@/lib/coaching/read` calls `canAccessFeatureData` NOWHERE — a call there would answer `true` anyway (a coach names no tenancy) and so would read like a gate while being none.
- ⚖ The two reaches never borrow each other's scope: the oversight readers start from the ORG (`getAccessibleChurchIds`), the coach reader from the ASSIGNMENTS (`coachesPlant`), and `@/lib/coaching/assignments` is the ONE implementation of "which plants does a coach reach" — `getAccessibleChurchIds` calls `assignedChurchIds` directly, with no wrapper of its own. An account holding both gets both answers, each in its own scope.
- A coach cannot write anywhere, and it is STRUCTURAL rather than a rule to remember: every write verb is `tenancy: "plant"`, which demands a non-null `users.church_id`, and a coach the INVITATION FLOW created has none. `/coaching/[churchId]` is the only `(dashboard)` route naming a church in its path, and the id in it is not authority — `readCoachedPlant` answers null for any plant the caller does not actively coach.
- Accepted residual: a SEEDED coach carries a `church_id` (see Dev Seeds) where an invited one carries none, so the seeded account opens `/people` and the invited one is bounced. The fixture is WIDER than the flow produces, so a check run against the seed is not a check of the flow. Retired by seeding the shape the invitation writes.
- ⚖ The sidebar's "Assigned plants" section is `assignedPlantsNavSection`, which returns `null` rather than an empty group when there are no active assignments — so the heading and the rows appear and disappear together.
- Reaching a plant is not permission to name the orgs BEHIND it: every org name on an oversight surface must be the caller's own or inside it, scoped in the `WHERE`.
- NO `/oversight` page reads the database.
- ⚖ `tasks.own` is the ONLY own-duty verb, because it is the only one whose subject is derivable: `tasks.assigned_to_id` references `users.id`, so `assertMayActOnTask` (`@/lib/tasks/service`) admits the assignee and falls back to `tasks.write`. It runs in the SERVICE after the row loads, so `/launch`'s milestone ticks get it too, and the bulk press applies it PER TASK — a refused row is a named failure beside "already complete", never a silent write.
- Accepted residual: AS-006's OTHER two own-duty writes — a Member's meeting RSVP and their own ministry team — still ship at `meetings.write` / `teams.write`, which is NARROWER than AS-006 describes: a team leader holding only a Member seat cannot yet make their team's writes. The reason they could not be `SEATED` is now GONE — `persons.user_id` (#378) is the subject half `ministry_teams.leader_id` and the meeting guest list needed — so what is left is the rewire itself, which is #495+'s and must re-make the widening argument against the link rather than assume it.
- A launch countdown compares two DAYS — floor `asOf` to its UTC day BEFORE subtracting a `yyyy-mm-dd` target. ONE implementation: `daysUntilTarget` (`launch/countdown.ts`).

## Authentication

→ [authentication](invariants/authentication.md) — sessions, `"use server"` modules, route handlers, `src/proxy.ts`.

- **Every export of a `"use server"` module is a POSTable endpoint reachable with no session and no UI** — the export list IS the auth surface. Keep helpers, reads and unwired writes in a sibling module with no directive.
- A state-changing action never takes its actor as an argument — it mints one from `verifySession()`. An entity implied by the actor is not an argument either.
- SESSION FIRST, THEN THE PARSE: the mint is the FIRST statement of the export, ahead of `safeParse`, because parsing first answers a sessionless caller differently for a malformed argument than a well-formed one.
- ⚖ AND THE MINT *IS* THE SEAT CHECK: every export of every `"use server"` module calls `requireSeat(capability)` first (AS-019, ruling 185 (8)) — it returns what `verifySession()` returned, so there is one statement, not two. The eight exceptions are named with their reason AND their `kind` in `UNSEATED_EXPORTS` (`sessionless` vs `non-seat-guard`); `seat-guard.test.ts` asserts that set EXACTLY and walks the rest.
- ⚖ A SESSIONLESS POST GETS ONE ANSWER, AND IT IS A THROW (#508). Where the guard sits inside an action's `try`, the `catch` opens with `rethrowUnauthorized(error)` (`@/lib/auth/unauthorized`) — converting it into `{ success: false, error: "You must be logged in…" }` hands an anonymous caller the well-formed answer the endpoint should never give. Moving the mint ABOVE the `try` (`tasks/actions.ts`, `settings/actions.ts`) satisfies it too and needs no rethrow; `server-action-surface.test.ts` walks every catch that still needs one.
- The refusal is `UnauthorizedError`, and its `SESSION_EXPIRED_DIGEST` is the ONLY thing `@/components/app-error` may claim sign-in expiry on — a client boundary gets no message in production, and every other 500 gets a sentence that does not diagnose.
- A `"use server"` directive is a MODULE PROLOGUE and nothing else. A function-level one publishes a POST endpoint the export-walk cannot see — it reads the exports of modules whose prologue carries the directive — so the form is banned outright and `inlineServerDirectives` fails the suite on one.
- WHICH capability each endpoint is guarded with is CHECKED IN (`@/lib/auth/capability-map`) and asserted with `deepEqual`. The walk proves a guard is called; only the map proves it was called with the right verb, so a permission change is a reviewable diff in one file.
- A seat refusal is a TYPE, `SeatRefusalError`, never `message.startsWith("Forbidden")` — `requireChurchAccess` and the invitation layer throw that prefix too, so a prefix test is a classification resting on prose.
- ONE permissions module, `@/lib/auth/seats`: `OWNER_ONLY` and `ADMIN_PLUS` are declared there and NOWHERE else, and one capability table pairs each verb with a seat set AND a tenancy requirement. A per-module matrix was rejected by name. `holdsSeatFor` is the non-throwing form for a sibling module holding an actor it cannot mint.
- A row naming TWO tenancies is refused EVERY capability including the reads — the check sits above the tenancy switch, because a `tenancy: "any"` verb would otherwise wave the defect through.
- A shared secret is never compared with `===`: use `matchesBearerSecret`/`constantTimeEquals`, which hash both sides to a fixed length first. Covers `CRON_SECRET` and `REVALIDATION_SECRET`.
- A request header the app does not write UNCONDITIONALLY is client input and nothing may branch on it. The trusted headers are `x-routed-url` (absence fails closed) and the platform-written `x-real-ip`.
- `x-routed-url` (`@/lib/routed-url`) carries the RELATIVE URL the proxy routed — path AND query — because a Server Component gets neither otherwise, and a layout is never handed `searchParams`. A route-scoping reader calls `routedPathname` for the route half; it does not get a second header.
- A signed-out bounce to `/login` goes through `loginPathFor` and comes back through `safeRedirectPath` (`@/lib/auth/safe-redirect`) — ONE param name (`redirect`), sanitised at BOTH ends. There are exactly TWO writers, `src/proxy.ts` and the `(dashboard)` layout; a page or a shared guard inside that group NEVER spells its own, because it can only race the two that carry a return path.
- ONE `"use server"` MODULE NEVER RE-EXPORTS ANOTHER'S NAMES, and `export type { … }` is not an exception: `next build` enumerates each action module's exports into the page's action manifest by NAME, so a re-exported type is registered as an action and then cannot be found. Import from the module that DECLARES it. Re-exporting from a directive-free module is fine; `server-action-surface.test.ts` resolves the specifier.
- ⚖ CHANGING THE LOGIN IDENTIFIER TAKES BOTH HALVES, AND ASKING TAKES A THIRD (CS-002, #616): `users.email` only ever holds an address somebody PROVED they can read, so `email_change_requests` holds the proof in flight and the swap needs the emailed TOKEN (the mailbox) *and* the SESSION (the account) — `confirmEmailChange` refuses a token issued to another account, so a forwarded link is inert. ASKING additionally demands the CURRENT PASSWORD: a session cookie is a bearer credential, the login identifier is itself a credential, and the notice to the old address is detection rather than prevention.
- WHETHER THE NEW ADDRESS ALREADY HOLDS AN ACCOUNT IS ASKED BY `users_email_unique` AT REDEMPTION AND NOWHERE ELSE. A refusal at request time is an enumeration oracle any account holder could run all day from a settings form; by redemption the caller has READ the mailbox, so naming what is true of it tells them nothing new. The violation aborts the whole batch, so the token survives for an address that later frees up.
- ONE LIVE REQUEST PER ACCOUNT, ENFORCED BY `email_change_requests_live_user_unique_idx` (partial on `consumed_at IS NULL`) — so the supersede must run BEFORE the insert in the same batch, and a mistyped address is self-correcting with no Cancel control to keep honest. `consumed_at` means "no longer live", not "verified": a redemption and a supersede both set it, because the column governs only whether the token still opens anything. Expiry is NOT in the index (`now()` is not immutable) and is asserted in the redemption's own `WHERE`.
- ⚖ THE TWO SELF-SERVICE CHANGES RIDE THE SIGN-IN GUARD, NEVER A SECOND COPY (CS-005): `email_change` and `password_change` are members of `authAttemptKinds` and rows of `RATE_LIMITS`, keyed on the account's OWN current address — never the address being asked for, which one account could spread across many mailboxes. `password_change` is `login`'s policy verbatim. `email_change` counts the REQUEST as an attempt that has not succeeded and records the SUCCESS at redemption, because there is no secret to get wrong when asking and the thing worth capping is a verification email nobody confirms; the clear-on-success (405-4b) then means only the account leaving requests unconfirmed meets the limit.
- A PASSWORD ROTATION AND THE REVOCATION OF EVERY OTHER SESSION ARE ONE `db.batch`, so there is no state where the password moved and a stolen cookie outlived it. The caller's own session is kept BY ID, from the cookie and never from an argument — a caller-named id would let a borrowed session keep itself alive and sign the owner out.
- `/verify-email` SITS UNDER `(dashboard)` AND SPELLS NO REDIRECT OF ITS OWN: the layout's bounce carries the return path, so a reader opening the link on another device signs in and lands back on the token. It REDEEMS ON A PRESS, never on the GET — link scanners and unfurlers fetch URLs they find in a message, and a single-use token spent by one of those leaves the real reader with a dead link.
- …and the REDEMPTION'S SUCCESS IS A PAGE, NOT A PANE (#658): `confirmEmailChangeAction` redirects to `/verify-email/confirmed`, which names the address out of the SESSION and reads no token. Two reasons, both measured. The asking URL carries a token that the swap has just spent, so a reload of it — the first thing an unsure reader does — answered the dead-link sentence about a change that had SUCCEEDED. And the sentence used to live in `useActionState`, where the update that would have shown it shared a transition with the tree patch `refresh()` streamed into the same response; the transition never committed, so the swap landed and the button sat on "Confirming…" forever while the refusal branch of that component cleared in ~2s. Do NOT generalise that to "a server `refresh()` strands a press": `requestEmailChangeAction` calls it from the same shape and renders correctly (driven on #658's preview). The outcome of a credential change belongs to the server; what stranded this one call site is unbisected and no longer load-bearing.
- `/login` IS NOT AN AUTH ROUTE in the proxy (`AUTH_ROUTES` is `/` and `/register`). The already-signed-in bounce is the login PAGE's, because it asks the session and the proxy can only ask the cookie — and a cookie that no longer verifies is precisely the reader the layout sends there, so bouncing on it closed an inescapable redirect loop.

## Seats & Tenancy

→ [seats-and-tenancy](invariants/seats-and-tenancy.md) — anything reading who an account is.

- `users.role` DOES NOT EXIST (dropped by migration 0051). An account is a SEAT — `users.seat` ∈ {owner, admin, member}, NULL for a coach — held in a TENANCY named by `church_id`, `sending_church_id` or `sending_network_id`. Neither half answers alone: `seat = 'owner'` says nothing about whose owner.
- ⚖ ONE OWNER PER TENANCY, ENFORCED BY THE DATABASE (AS-002, ruling 185 (4)): three partial unique indexes, one per tenancy FK, each `WHERE seat = 'owner'`. This RETIRED the OB-010 claim race — a second Owner is now a write that cannot commit, not a defect to detect. The `notExists` in `claimPlanterStatements` stays only to make the ordinary already-claimed case a no-op instead of an error.
- The partial predicate and the NULL-distinct rule are BOTH what keep a coach-only account writable — no tenancy, no seat, caught by neither half. An index made total, or a `seat` made NOT NULL, breaks the second coach account with nothing in the app to say why.
- ONE function answers "which tenancy is this", `oversightOrgOf` (`@/lib/auth/tenancy`, an import-free leaf), and it answers ONLY for a row naming EXACTLY ONE tenancy FK. A row naming two is a data defect that reaches NOTHING in either direction; `isChurchLevelUser` is stated positively for the same reason, so the defect is neither church-level nor oversight.
- A ROUTE HANDLER IS NOT COVERED BY ANY OF THIS. The seat guard and its walk are about `"use server"` exports; anything under `src/app/api/**` is a separate surface with its own auth (`memory/contracts/api.md`), and adding a route handler that writes feature data needs its own `requireSeat`/`assertSeatFor` call, chosen deliberately.
- Accepted residual: nothing in the schema holds an account to one tenancy. Migration 0050 §1 cleared the twelve rows that carried two (measured on the shared branch, 2026-08-20), but a CHECK would have refused them, so the state stays REPRESENTABLE and every reader fails closed on it. Retired by a `num_nonnulls(...) <= 1` CHECK once no writer can produce one.
- Outside registration a seat is granted in exactly ONE place — the OB-010 claim on a plant with no Owner, promoting `{owner, member}` and NOT `admin`. The pair is the ruled `{planter, team_member}` migrated; `admin` is a seat the role model could not express, so admitting it would be a widening, not a rename.
- An authority arm that names an oversight org asks the SEAT as well as the tenancy (`isOrgOwner`) — `sending_church_admin` and `network_admin` each meant "the Owner seat in this kind of org", so a seatless org row and an org Member were already refused. Dropping the seat half widens the rule while looking like a rename.
- REMOVING A SEAT CLEARS THE TENANCY AND THE SEAT AND NOTHING ELSE ABOUT THE PERSON (AS-016). The account ROW survives, and the `persons` row and its `team_memberships` are untouched — a person record and an account are separate things, so losing the login must never lose the roster entry. The cascade's other three effects are sessions deleted, OPEN tasks (`status <> 'complete'`) reassigned to the Owner, and `ministry_teams.leader_id` nulled for the teams that account's own person record led.
- A REMOVAL CLEARS ALL THREE TENANCY FKs, NOT ONLY THE ONE IT ACTED ON, AND THAT IS A SECURITY RULE. A row naming two tenancies is representable (the accepted residual below) and reaches NOTHING, because `oversightOrgOf` answers only for exactly one FK. Clearing `church_id` alone would leave the row naming exactly one and PROMOTE the removed account into that org's oversight surface — `requireOversightUser` admits on the FK alone and never asks the seat. A removal must never widen reach.
- The removal is ONE `db.batch` with the TENANCY CLEAR LAST, and every statement carries the actor's `church_id` (the sessions delete through an `exists`, its subject being keyed by the account). The three earlier statements are redo-safe, so a replay re-runs three no-ops. `db.batch` is all-or-nothing on FAILURE only — a zero-row UPDATE is a success — so the marker RETURNS and the caller refuses on an empty rowcount rather than reporting a removal that changed nothing. `src/lib/seats/roster.test.ts` fails on a reorder, a missing scope, or a dropped rowcount check.
- ⚖ Ending a coach assignment is `coach.assignment.manage` (ADMIN_PLUS, plant), NOT `seat.manage` — coaching is an assignment, never a seat, and AS-004 already gives an Admin the power to invite a coach (ruled 2026-08-21 for #497).
- Accepted residual: any plant Admin may end a coach assignment, not only the Admin who created it as AS-018 words it. `coach_assignments` still records no author — #496 shipped the invitation surface WITHOUT adding one, because the assignment is written by an `INSERT … SELECT` off the invitation row and `inviter_user_id` already names the Admin there. Retired by carrying that id onto the assignment.
- ⚖ A WRITE AFFORDANCE IS HIDDEN, NEVER DISABLED, for a context that may not use it (AS-020, #499). A `disabled` control still reads out to a screen reader and still advertises a power the viewer does not hold, so a capability spent on the `disabled` attribute is a FAILED hide — `read-only-surfaces.test.ts` matches that shape (`disabled={!can…}`) over every checklist file and fails on it. A control that is `disabled` for a PENDING, validation or business reason is untouched by the rule.
- ⚖ …and the hide is read off the SAME capability table `requireSeat` refuses the POST with, through two transports and one decision: a SERVER component asks `holdsSeatFor(user, cap)`, a CLIENT component asks `useCan(cap)` (`@/components/shared/viewer-capabilities`), seeded once per request in the dashboard layout by `heldCapabilities(user)`. Never a `canWrite` boolean threaded through a component tree, and never a second rule — the two failure modes it forecloses are a button that always refuses and a button hidden from somebody the server would have said yes to.
- `useCan` FAILS CLOSED with no provider, unlike the sibling contexts that throw. A hidden control is one button fewer; a throw inside a shared component takes down the marketing embeds that render `PeopleList` and `QuickActions` with no session. The alarm for an unmounted provider is a test over the layout, not a runtime error.
- EVERY PLANT SURFACE REFUSES AN ACCOUNT WITH NO `church_id`: each route under `(dashboard)` that reads a plant's records opens with `verifySession()` then `if (!user.churchId) redirect(…)`. `read-only-surfaces.test.ts` walks the route tree and fails on a new plant route that forgets it, so the property survives routes nobody has written yet. A coach minted by the invitation flow has no tenancy FK at all (`assignCoachOnAcceptStatement` writes only the `coach_assignments` row), and an org Member's tenancy is an oversight FK — so neither reaches rows 2-13 of the read-only checklist.
- …BUT THAT GUARD READS A TENANCY, NOT A SEAT, AND A GATE MUST NEVER BE DELETED ON THE STRENGTH OF IT (#499, found in the browser). A SEATLESS account that DOES hold a `church_id` is representable, and `scripts/seed-dev-db.ts` creates one deliberately — the dev coaches are `seat: null` with a `churchIndex`, because the FK is what gives them a notification feed. Signed in as one, `/people` renders in full. What refuses the writes there is the capability hide and `requireSeat`, not the redirect. The hide is load-bearing on every plant surface, not defence in depth behind a wall.
- ⚖ The FRD's read-only surface checklist and `READ_ONLY_SURFACE_CHECKLIST` (`@/lib/auth/read-only-surfaces`) are kept in parity BY A TEST that parses the FRD's markdown — both columns, row for row. Neither side can be edited alone, which is what makes "every row was walked" a property rather than a claim.
- ⚖ TICKING A LAUNCH MILESTONE SURVIVES FOR A MEMBER, narrowing the checklist row's wording against the capability table (ruled 2026-08-22, #499). LS-007 split `launch.milestone` (SEATED) from `launch.schedule` (OWNER_ONLY) on purpose so milestone completion follows ordinary task rules. Hiding it would refuse in the UI what the server allows — the OVER-hide, which is the same drift as an under-hide and is what the positive render tests exist to catch. The same reasoning keeps every `read` and `self.write` control visible: export, downloads, print, bookmarks, reading progress, notification preferences, insight and product feedback.
- ⚖ …and the same rule keeps a Member's OWN assigned task's complete control: `tasks.own` is SEATED, so the row's control is gated on `task.assignedToId === viewer`, not on the seat. That mirrors `mayActOnTask` in `@/lib/tasks/service` exactly. `addSubtaskAction` asserts against the PARENT and `setSubtaskCompletionAction` against the SUBTASK's own row, so owning a parent does not buy the tick on a step assigned to somebody else.
- Accepted residual — ⚖ THE CHECKLIST'S TEAM-LEADER EXCEPTION CANNOT SHIP, and no surface may fake it (#499). The row says "a team leader's writes on their own team stay, derived from `MinistryTeam.leader_id`", but `leader_id` references `persons.id` while a session names a `users.id`, and no column joins them until AS-013's registration link lands. `team.leaderId === user.id` compares two id spaces and is false for everyone for ever. So every teams write stays hidden for a Member, which matches what the server does — the same reason every teams verb sits at `teams.write`. Retired by the account-to-person link, which restores both halves at once.
- Accepted residual: a Member loses the CSV import template download, which is `read`, because it lives inside the import wizard the sweep hides whole. The FRD names "import" explicitly, so the flow goes as a unit; retired by moving the template download out of the wizard if anyone asks for it.

## Phase Engine — Cited Facts & Attestation Citations

Applies to `src/lib/phase-engine/**` and the `/phase` surfaces rendering `plant_insights.cited_facts`.

- A CITED PATH IS UNTRUSTED INPUT — the judge writes it, so a segment may be `constructor`, `toString` or `__proto__` — binding every read of a judge-written key AND the write that assembles `manual.byKey`. Exactly three shapes are sanctioned: a `Map` read with `.get`, a `Record` read through `Object.hasOwn`, or a prototype-free `Object.create(null)` accumulator; never a bare `in` or `[key]`.
- ⚖ THE RULE THE JUDGE IS TOLD AND THE RULE IT IS HELD TO ARE ONE ARRAY (#538). The active rubric body INTERPOLATES `NETWORK_VERDICT_PHRASES`; never retype the ban-list into rubric prose. A hand-kept second copy went short by two phrases, so the judge could emit a word it was never shown and have the whole response rejected for it.
- ⚖ SHIPPING A RUBRIC VERSION IS A ONE-LINE FLIP OF `ACTIVE_RUBRIC_VERSION`, and every superseded version STAYS in `RUBRICS`. Assessments store the version that produced them, so deleting v0 would silently re-explain historical assessments against text their planter never saw.
- EVERY RULE THE JUDGE'S OUTPUT IS HELD TO IS A REFINEMENT ON THE SCHEMA `judgeOutputSchemaFor` BUILDS FOR THAT PLANT, never a check after the parse and never rubric prose alone — a post-parse throw is invisible to the retry ladder, so audience coverage was fatal on the first draft while the other three rules were re-prompted (#605). Each refinement tags its issue with a name from `JUDGE_RULES`, which is what the log and the re-prompt both read.
- SO THAT SCHEMA IS A FUNCTION OF THE PLANT'S EVIDENCE PROFILE, and no snapshot-free spelling of it exists (#635) — "unknown is not healthy" cannot be asked of a draft without knowing what each lens knows. ONE profile per run: the same value grounds the prompt and holds the draft, because judging a model against a profile it was never shown is #538's shape one file over.
- ⚖ UNKNOWN IS NOT HEALTHY, AND THAT REFUSES THE `positive` BAND ONLY (#483 C17, ruled #635 2026-08-22, both audiences). A lens with nothing measured and nothing attested may carry no positive insight — `unknown_lens_not_healthy` — while the neutral `info` band stays available, because a cold-start planter is owed the absence named and the first step, not eight blanks. The three prompt passages offering "pair with a positive insight, it's free" name the blind lenses where that device is unavailable; `buildCsfScorecard` drops a pass a blind lens never earned so rows stored before the rule render the insufficient-evidence tile.
- THE TWO LADDERS AROUND `generateObject` ARE NOT INTERCHANGEABLE: `runPacedCall` repeats a call for a provider that would not answer (#36), and `runAssessment`'s bounded schema ladder re-prompts WITH the rejecting rule for a provider that would not follow one (#605). Sending a rejected draft back through the throttle ladder draws the same mistake — four gpt-4o calls and ~48s per plant — and leaves nothing in the ladder for a real 429.
- A CORRECTION CARRIES EVERY RULE BROKEN SO FAR, not just the newest draft's (`carryCorrectionForward`). The observation budget and the pairing rule pull against each other, so a model holding one message trades one for the other draft after draft; on the fleet that burned a plant's whole ladder while every draft honestly fixed what it was last told.

## Wiki Articles

- **Never interpolate a slug into a wiki path.** Build every one — `href`/`router.push`, OpenGraph `url`, the active-item test — with `wikiHref()`, which encodes per segment so `/` stays a separator.
- Bookmarks, recently-viewed and last-in-progress store SLUG-ONLY rows and re-resolve each through `getArticle`, whose `churchId` defaults to `null` — so on that default a church's own article resolves to `null` and the surrounding `.filter(Boolean)` drops it SILENTLY.
- `getArticles` is request-cached (`React.cache`) and its docblock does NOT say what that costs: a mutate-then-read inside ONE request goes stale. Revalidate and let the next request read, rather than reaching around the cache.
- A church's published row for a slug overrides the global one in SQL and ONLY in SQL: a JS collapse cannot answer for a RANKED read, because it sees only the rows that survived the `ts_rank` cut and the church's rewritten copy need not be among them. The test pins the ABSENCE of a second implementation, never that reason.
- Cross-links live ONLY in `related_article_slugs`, never in an article's prose and never seeded: a prose link duplicating the column renders that link twice. No test catches a violation.
- ⚖ 2026-08-22 (#631): an aggregate counts the population of the surface it sits on. `/wiki/progress` gets BOTH halves from one `getProgressStats()` — `summariseProgress` intersects the reader's `wiki_progress` rows with the corpus `getArticles` returned — so a completion on an article since unpublished or overridden away cannot outlive its denominator. Never clamp the percentage; the two numbers come from one read or the read is wrong.

## Profile Photos — person photos and account pictures

Applies to `persons.photo_url` + `src/app/api/people/[personId]/photo/route.ts` + `uploadPersonPhotoAction`, and to `users.avatar_key` + `src/app/api/account/avatar/route.ts` + `@/lib/auth/avatar` (CS-004, #617, #654). P-024 is ONE rule with two subjects: everything below holds for both unless a bullet names one.

- The column holds a PRIVATE-BUCKET STORAGE KEY, never a URL. `persons.photo_url`'s name says otherwise and is the reason every reader of it needs a docblock; `users.avatar_key` was named after that lesson. The only address a browser gets is an app route that checks the session before streaming bytes — no signed URL reaches the page, because a signed URL is a bearer token anyone can pass on.
- ⚖ THE PERSON ROUTE TAKES AN ID AND THE ACCOUNT ROUTE TAKES NONE, and the difference is the authorization. A planter reads OTHER people's photos, so `/api/people/{id}/photo` pays for its id with a church-scoped lookup (a foreign `personId` reads as MISSING, not forbidden). An account only ever reads its own, so `/api/account/avatar` has no id at all — nothing to forge, nothing to enumerate, and no check to get wrong. Never add an id to it "for symmetry"; that is the moment the check becomes necessary.
- ONE WRITER PER COLUMN, each in a small module of its own — `setPersonPhoto` in `src/lib/people/person-photo.ts`, `setUserAvatar` in `src/lib/auth/avatar.ts`. Both modules hold the column's WHOLE business (its read, its writer, its effects seam) and nothing else, which is what lets the ratchet fence each one by file: a key named anywhere else in the tree fails. It lived in the 700-line `people/service.ts` until #654, where the fence had to permit ten client-facing reads to permit the writer — and the input schemas deliberately have no field for the key. A `FormData` bag is shaped by the POST, so a key there would let a caller aim their own row at another tenant's object and read it through a route that trusts the stored key. REMOVAL IS THAT SAME WRITER WITH A NULL KEY (P-024b), never a writer of its own — upload, replace and remove then share one spelling of the ordering below.
- Upload BEFORE the row points at the object, delete the old object AFTER it stops (same asymmetry as Generated Documents). A failed delete is collectable garbage; a row naming a missing object is a picture nothing in the app can repair — the route answers 404 for it and the initials fallback renders.
- The delete half lives INSIDE the writer, not in its callers, so no caller can forget it or hoist it above the row write; `people/photo-ordering.test.ts` and `auth/avatar.test.ts` run the sequence against forced failures rather than reading the source, the way `GeneratedDocumentEffects` does.
- ⚖ THE STRIP FAILS OPEN, and `client-boundary.test.ts` pins `persons`' column list because of it. Every read in the people domain is `db.select()` then `toPersonForClient`, so a column added to `persons` reaches the browser by default, with no compile error. A hand-written projection would fail closed but a silent omission and a deliberate strip read identically in a diff — so the default stays and the ratchet is a pinned column set: add a column and CI fails until somebody decides whether it crosses.
- NEITHER KEY CROSSES TO THE BROWSER, and the asymmetry that used to sit here is retired (#654). A prop on a `"use client"` component rides to the browser in the RSC payload whether it is drawn or not, and so does a server action's RETURN VALUE — two channels, and #617's first draft leaked through the second (`AvatarOutcome` carried the key; nothing read it; the prop scan could not see it). The account half stops the key in `userAvatarSrc`, called in the dashboard layout and the Account section. The person half stops it in `toPersonForClient` — THE SAME BOUNDARY THAT ALREADY DROPPED `user_id`, which is why closing it was a one-line trade rather than a new mechanism: the strip removes `photo_url` and adds `photoSrc`, the route it resolves to. Every person surface that draws a face reads that route and no client surface can reach the key, because the type no longer has one.
- `src/lib/picture-key-boundary.test.ts` is the ratchet for BOTH keys, and it asks ONE question: where may this key be named at all? A per-key allowlist of server files, scanned across `src/`, so a prop leak and a return-value leak are the same failure — including the shape both earlier scans AND `tsc` walk past, a key parked in a variable before it is returned (excess-property checking applies only to a fresh literal returned directly). `photoKey` is fenced beside `photo_url`, because renaming a variable is the cheapest way past a scan that knows one spelling. `scripts/prove-picture-key-fence.sh` puts each of the four leak channels back and asserts the fence goes red — a guard that ships broken stays green, which #617's did twice.
- ⚖ `getPerson` DOES NOT HAND OUT THE PHOTO KEY, so the server-side callers that need it read it through `getPersonPhotoKey`, church-scoped like everything else. It answers `null` for no such person and `{ photoKey: null }` for a person of ours with no photo, and `setPersonPhoto` is what needs those apart: it must not write for a foreign person and must write for a person whose first photo this is. The ROUTE collapses them again on purpose — `storedImageResponse` answers one 404 for both, so a browser cannot tell "not your person" from "no photo".
- AN UNDEFINED `src` IS ALSO how a client learns no picture is set (`avatarSrc`, `photoSrc`) — a boolean beside it would be a second prop that can disagree with the first.
- ONE CONTROL SERVES BOTH SUBJECTS: `src/components/picture-field.tsx` (#654). The two surfaces shared `usePendingPicture` but kept near-clone markup, and the clones had already drifted — only the newer one had the accessibility work. Every difference that remains is a row in that file's `SUBJECTS` table (the copy, and the avatar size); a difference not in the table cannot exist. `avatar-field.tsx` and `person-photo-field.tsx` are now action wiring only. A third picture surface is a row, not a file.

A second copy of it for a second subject is how those three stop agreeing.

## Rich Text — Stored HTML & the Sanitiser

→ [rich-text](invariants/rich-text.md) — `src/lib/rich-text/**` and every writer or reader of a rich-text body.

- The SERVER is the gate, never the editor — every compose/task action is a POSTable endpoint that never saw the toolbar — and there is ONE sanitiser, `sanitizeRichText`, allow-list only.
- ONE door converts a stored value for reading or editing, `toRichTextHtml`, and ONE read-only renderer draws it, `RichText`. A hand-rolled `dangerouslySetInnerHTML` is a second copy of both.
- ONE door substitutes merge values into an email body, `renderEmailBodyHtml` (`communication/merge.ts`) — escape the values, turn their newlines into `<br>`, then drop the LINE a field that resolved to NOTHING would have filled. All three readers call it: the send path, the compose preview and `RichText` (the sent-message page re-substitutes, because `body_html` is stored UNRENDERED). A second spelling draws a different email from the one that went out. `renderEmailBodyText` drops the same line, so the two halves of one email break in the same places.
- THE UNIT OF THAT DROP IS THE LINE, not the paragraph: the date and the location are two lines of ONE paragraph, and a paragraph-scoped rule could only take them together or not at all — it took neither, and a meeting with no location shipped a bare 📍 (#625). A block (`<p>` or `<li>`) whose lines all go is dropped whole, which is the `{{meeting_agenda}}` case (#612) falling out of the same rule.
- "The line is only this token" is asked of its VISIBLE TEXT (`richTextToPlainText`), never of its markup — one predicate for both halves of the email, so they break in the same places. Matching raw HTML let any inline wrapper hide the token, and a planter who bolds `{{meeting_location}}` got `<em></em>` plus a dangling `<br>` in the HTML while the text half dropped the line. A line whose tags do NOT close inside it (`<em>a<br>{{x}}</em>`) is kept: deleting it would leave the wrapper open all the way to the inbox.
- That drop is decided against the TEMPLATE, before substitution — a line holding one token whose value is `""`. Never against the rendered body: `<p><br></p>` is also how this product spells a blank line the planter typed, so a post-render sweep for empty paragraphs silently restyles every outgoing email. A token nothing resolved keeps its line, so the preview can still flag it.
- Line breaks are normalised (`\r\n` and lone `\r` → `\n`) before any of those rules count or collapse lines, and a rendered SUBJECT is collapsed to one line — a subject is an email HEADER, and `{{meeting_agenda}}` is the first merge value with line breaks in it.

- ⚖ A vision meeting's follow-up tasks go to the FIRST-TIME attendees and to nobody else (VM-007, #323): `followUpRecipients` (`tasks/events.ts`) reads the `attendance_type` the register already derived, and `null` is unknown rather than first-time. Returning and core-group attendees get none.

AN INDEX PREDICATE WIDER THAN THE READ IT GUARDS IS A SUPPRESSION VECTOR — that is the general shape, and the two spellings change together.
- EVERY ROW THE GENERATION INSERT WRITES HAS AN ARBITER, so the statement is PER-ROW idempotent (#521): `tasks_person_follow_up_unique_idx` over (church_id, related_id, due_date) for live person follow-ups joins the evaluation index, and the INSERT carries an UNTARGETED `ON CONFLICT DO NOTHING` — untargeted because a named arbiter covers one index and re-raises on the other. All-or-nothing became the WORSE shape once follow-ups had a key of their own — a race whose `owed` sets differ aborted the wider racer whole and dropped the late-added first-timer the handler was made convergent for.
- ⚖ The answer to a phase-template prompt belongs to the PLANT, not to the planter: the key is the transition alone and `/tasks` has no role gate, so any church member who opens it first answers for everyone. - Accepted residual: `findOpenInSeries` is a SELECT-then-INSERT, so two instances of one recurring series completed concurrently each mint a successor. The honest fix is a partial unique index on the series key for open rows.
- Accepted residual: `wouldCreateCycle` is a SELECT-then-INSERT with no `FOR UPDATE`, so two concurrent writers adding opposite edges each read an acyclic set and commit a cycle; the unique index stops only a duplicate of the same pair. Retired by a serialising guard over the church's edge set.

## Notifications — the shared F11 queue, from a consumer's side

- ⚖ A weekly digest lands SUNDAY 16:00 in the CHURCH's zone by DEFAULT, and the day and hour are a CHURCH SETTING — `churches.digest_send_weekday` / `digest_send_hour`, whole hours only, range-checked by `CHECK` (N-013, ruled 2026-08-15, superseding Monday; shipped #448). The hour carries the rule: at the UTC period boundary a Sunday digest arrives Saturday evening in the Americas. The WEEKDAY governs the weekly cadence only, the HOUR governs both. The CHURCH sets when; the RECIPIENT still sets whether and how often.
- A digest PERIOD is `[send hour, next send hour)` resolved on the CHURCH's wall clock through `instantAtZonedHour`, never 24-hour arithmetic — so a DST period is 23 or 25 hours and the send time does not drift twice a year. Every instant falls in exactly one period of each cadence; that partition is what "once per recipient per period" rests on.

The sweep therefore walks COHORTS — one keyset scan per distinct (zone, weekday, hour) — which is what keeps its owed test an `IN (two literals)` (#448).
- A `DigestCohort` is the three columns AS STORED, never the coerced anchor. The selection filters `churches` on the stored tuple and derives the keys through `digestAnchorFrom`; keying a cohort by the coerced value would leave a row that failed coercion listed under one cohort and selected by none — a digest owed forever, silently. ## Migrations

- A MIGRATION IS TWO FILES — the `.sql` and its `meta/<n>_snapshot.json`, which records the schema it leaves behind. `drizzle-kit generate` diffs against the NEWEST snapshot on disk, so a schema-changing migration that ships without one makes the next generate re-emit its DDL inside SOMEBODY ELSE'S migration: 0059 shipped bare and 0060 re-created `plant_assessments.planter_seen_at` (#592). A DATA-ONLY migration has no snapshot and needs none, so the property `src/db/migrations.test.ts` holds is the one that matters — the newest snapshot still equals `src/db/schema` — and the repair is `scripts/backfill-snapshot.ts`, ABOVE the newest snapshot only: a bare migration below one is already absorbed by it (why 0059 needed no backfill and 0061 did).
- …and `pnpm db:generate` FORMATS that snapshot, because nothing else will. Prettier runs from a `PostToolUse`/`afterFileEdit` hook on files an AGENT writes; drizzle-kit writes the snapshot itself, so it reaches CI raw and fails `format:check` while every local check passes (#617 lost a CI round to exactly this). The prettier pass is the third link in the `db:generate` chain — do not drop it, and do not "fix" a raw snapshot with `pnpm format`, which walks the whole repo. It globs `meta/*.json` rather than the new snapshot alone, so a `db:generate` run that meets an OLDER raw snapshot reformats that one too and puts an unrelated file in your diff: that is the glob doing its job, not a mistake to revert.
- RESERVING AN `idx` DOES NOT RESERVE AN ORDER — `when` decides. `drizzle-kit migrate` applies a migration only while the ledger's MAXIMUM `created_at` is below its `when`, so a sibling holding a lower `when` on another branch is SILENTLY SKIPPED: exit 0, nothing applied. Such a migration owes its sibling a FORWARD reconcile in its header.
- …and the re-stamp is `previous.when + 1000`, ONE SECOND, never plus a day — a size no TEST can hold you to: `db/migrations.test.ts` → "the journal never regresses" enforces THAT `when` rises and cannot enforce BY HOW MUCH, so both spellings pass CI. A day-sized bump pushes the journal past the wall clock, and every migration generated before real time catches up then lands below the tail and fails that guard through no fault of its own — 0055–0057 walked two days ahead exactly this way (#190).
- ⚖ A RENUMBERED migration ships with an OPERATOR RECONCILE step or it does not ship: `drizzle-kit migrate` never asks whether THIS migration's row is present, so a database that applied the OLD number is invisible to it, the DDL re-runs and the apply aborts on `column ... already exists`. The header carries the detection and both exits.
- ⚖ A CHECK REJECTS ONLY `false`, so a constraint that evaluates to `NULL` ACCEPTS the row. `(kind = 'seat' and seat in (…)) or (kind = 'coach' and seat is null)` reads as an ⟺ and admits `kind='seat', seat=NULL` (`true and NULL` = `NULL`). Write the biconditional over non-null booleans — `(kind = 'seat') = (seat is not null)` — and PROVE a new constraint by writing the row it forbids, never by reading the DDL.
- …and a SCRIPT applies that size, so it no longer rests on remembering (#566): `scripts/restamp-migration.ts` moves the TAIL ONLY to `max(its own, highest sibling + 1000ms)` and `pnpm db:generate` runs it, which stamps generation at `max(Date.now(), floor + 1s)`. It rewrites the journal AND the migration's own header — the only two places a `when` lives, snapshots carry none — and it anchors on the OLD NUMBER, never on `created_at = `, because a header also names SIBLING rows an operator must delete (0048 lists three, 0049 ten). Entries behind the tail are history: no stamp of theirs and no `tag` ever moves.
- ONLY AN UNAPPLIED MIGRATION IS RE-STAMPED. Moving a `when` orphans the ledger row written under the old one, so `drizzle-kit migrate` re-applies the DDL and aborts on `already exists` — the failure the ⚖ renumbering rule below exists to prevent. A hand re-stamp of a tail any database already applied owes that database the `UPDATE drizzle.__drizzle_migrations SET created_at = …` the script prints.
- ⚖ THE LEDGER IS DIAGNOSED READ-ONLY: any write to `drizzle.__drizzle_migrations` is ATTENDED-ONLY, never a side effect of another track, and `_journal.json` is never edited to invent a tag for a hash no committed blob matches. An applied row the journal cannot name is ACCEPTED HISTORY — deleting it hides applied DDL nobody can name; the check and both orphans are in [`contracts/db.md`](contracts/db.md) → Migration ledger vs journal.
- A MIGRATE RUN IS ONE TRANSACTION OVER THE WHOLE PENDING BATCH, not one per migration: the maximum `created_at` is read ONCE up front, then every entry above it applies inside a single `begin`/`commit`. So a failure rolls back the ledger rows it just inserted too — the ledger after a failed run is byte-identical to before it, and EVERY attempted entry is still pending. Never infer "the first pending one is the one that failed"; the pending list is the search space and the catalog is the evidence (#577, proven on a scratch database 2026-08-21).
- …which is why `pnpm db:migrate` is `scripts/db-migrate.ts` and not bare `drizzle-kit migrate`: the CLI swallows the driver error and exits 1 with an unfinished spinner and NOTHING on stdout or stderr, so a 42701 from a renumbered migration is indistinguishable from a bad password. The wrapper prints the attempted batch, the objects already in the catalog that an apply collides with, and the SQLSTATE each would raise — SELECTs only, and it subtracts a migration's own `DROP`s so 0025 and its three siblings are not accused of colliding with the index they drop first.

## Date & Time Rendering

→ [dates-times](invariants/dates-times.md) — anything rendering or parsing a date.

- Never format a `Date` without a pinned `timeZone` — format through `src/lib/datetime.ts`. Church-scoped surfaces take the church's IANA zone as an argument (plumbed down, never a global); `APP_TIME_ZONE` (UTC) remains the pin for meeting wall-clocks and surfaces with no church. `Intl`/`toLocale*`/date-fns follow the runtime's zone, so SSR and hydrated markup differ (React #418).
- The CALENDAR-DAY primitives live in `datetime.ts` and nowhere else: `MS_PER_DAY`, `toCalendarDate(date, timeZone?)`, `addCalendarDays(from, days)` — every `date` column written by tasks, ministry-teams and launch goes through them, so the day a write NAMES is measured in the zone it is READ in. Not yet absolute: a ten-site debt list lives in [dates-times](invariants/dates-times.md) — route a call site whenever you touch its module; a NEW local day constant or a re-export is the mistake this line stops.
- The WALL-CLOCK primitives live there too, and are the only two: `zonedHour(date, timeZone)` and `instantAtZonedHour(calendarDate, hour, timeZone)`. `MS_PER_DAY` may be added to a calendar-date STRING (a day index) but NEVER to an instant that has to keep a wall clock — a DST day is 23 or 25 hours. `instantAtZonedHour` resolves the hour that happens twice to the FIRST occurrence and the hour that never happens to the instant the clock jumps to, so consecutive days tile the timeline with no gap and no overlap (#448).
- ⚖ Every church has a non-null IANA `time_zone` defaulting to `America/Chicago` (existing rows backfilled). Invalid ids are rejected on write. Church-scoped instants render in that zone; there is no per-user timezone, and onboarding does not ask.

## Client/Server Data Synchronization

Conventions and examples: [`contracts/data-patterns.md`](contracts/data-patterns.md).

- NEVER store server data in `useState` (it goes stale the moment the server revalidates) and NEVER sync data with `useEffect` — server data flows through props from server components.
- ⚖ ONE EXCEPTION, AND IT IS PRESENTATION RATHER THAN STATE: **cached section data is permitted as STALE-WHILE-REVALIDATE only** (ruled 2026-08-22 for #673, the settings modal). A cached response MAY paint instantly, and a revalidation MUST be in flight whenever the cached key's `serverRenderId` is not current; the fresh answer replaces it. In `settings-hash.ts` that is one module-scope map keyed (scope, section, `serverRenderId`, attempt), and the cached view is read at exactly one call site — as the Suspense FALLBACK for the read at the current render id — so it is on screen only while its own revalidation is running. Nothing puts it in `useState`, no `useEffect` syncs it, and nothing derives from it. FAILURES ARE NEVER ANSWERS: `{ ok: false }` in all three of its shapes is kept only to stop the replay loop and is never cached as CONTENT; a section with no held answer falls to the skeleton, and one that HAS a held answer paints it while the read is pending and then shows the failure and its Retry when the read comes back. Anything wider is the rule above and not this exception: a cache keyed by anything other than an account and a server render id, or a cached value painted with no revalidation running.
- ⚖ …AND A CACHE KEYED ONLY BY THE DOCUMENT IS A CROSS-ACCOUNT DISCLOSURE (#673, measured on the preview). "Module scope dies with the tab" is TRUE and NOT ENOUGH: signing out is a server action ending in `redirect()`, and a server redirect is a CLIENT-SIDE navigation that reuses every shared layout segment (→ the `revalidatePath` rule above, measured for #658), so `/login` and the dashboard share the root layout and THE DOCUMENT SURVIVES THE WHOLE ACCOUNT CHANGE. The first draft of #673 shipped without an identity in the key: a coach signed in after a sending-church Owner on the same tab, opened settings, and the first painted frame carried the PREVIOUS reader's name and email address before their own answer replaced it. The dashboard layout therefore passes `scope={user.id}` beside `serverRenderId`, it is the first segment of the read key, and a read at a new scope EMPTIES the map. The two props answer different questions and neither can do the other's job: `serverRenderId` says WHEN an answer was true and is deliberately ignored when a cached section paints (serving an older render's answer is the whole feature), so `scope` is what says WHO it was true for. A gated section is never held either, because the prefetch walks `visibleIds` and a typed fragment for one is answered `refused`.
- Use `useOptimistic` for instant feedback; the server action calls `refresh()` from `next/cache` to reconcile, not the client calling `router.refresh()`. Example: `ActivityTimelineClient`. Props-only is the other shape (`TagPicker`). ⚖ ONE EXCEPTION, and it is about WHEN: when the same action is also reached by a click that NAVIGATES, the refresh moves to the client, because only the caller knows whether it is staying — and therefore whether the refresh runs inside the press or after the push (`notification-feed.tsx`, #228, #527).
- ⚖ …AND ITS THIRD SHAPE: AN ACTION THAT NAVIGATES ITSELF keeps `revalidatePath` and drops `refresh()` (#658, `confirmEmailChangeAction`). A server `redirect()` is a CLIENT-SIDE navigation, so it reuses every layout segment the two routes share — the confirmation landed on "you now sign in as `<new>`" beside a sidebar still rendering the OLD address, measured on the preview. `revalidatePath("/", "layout")` and not a path, because the signed-in identity is chrome: it is on every screen the account can reach, not on the one it lands on. The `refresh()` goes, because the tree it would patch is the tree the redirect replaces. Same rule as #529's "an action whose only caller leaves", reached from the action's side instead of the click's.
- ⚖ A CLICK THAT NAVIGATES OWNS NO SYNCHRONOUS WORK ON THE ROUTE IT IS LEAVING (#228, #308). A `<Link>` whose `onClick` also fires a server action must call it plainly — not in `startTransition`, and not through an action that calls `refresh()`. Either one turns the click into work React owns on the route being LEFT: a transition entangles the push behind an update suspended on a round-trip, and the refresh re-renders the route the push is replacing. Measured on #308's preview, both strand the navigation (22/22 and 11/11) while the write still lands, which is the "it marked read and went nowhere" bug; with neither, 22/22 navigate. There is no optimistic state to keep on a page the user has left.
- ⚖ …BUT IT STILL RECONCILES, ONCE THE PUSH HAS COMMITTED AND PAINTED (#527): `void action(id).then(() => whenPushCommits(leaving)).then(() => router.refresh()).catch(() => {})`, where `whenPushCommits` waits for `location.pathname` to leave the route the click started on and then one more frame (double `requestAnimationFrame`, 3s cap). Skipping the reconcile is a bug, and #308 shipped it skipped on a FALSE premise — "the destination's own render is a fresher read". A client-side push REUSES the layout segments both routes share rather than re-rendering them (partial rendering; `.next-docs/01-app/02-guides/authentication.mdx:1350`), and the shell's bell sits in exactly such a shared layout, so nothing re-read it on arrival: 25 unread, row click, `read_at` set, bell stuck at 25 for the session (12/12 navigated, 0/12 counted, on the pre-#527 preview).
- …and the two waits are separate claims, both measured on #527's preview. AFTER THE ACTION is not after the push — the action settles in 200–500 ms and the push commits in 180–430 ms, so they overlap and it still stranded 8 of 11. AFTER THE URL CHANGES is not after the destination RENDERS — the URL is written when the router starts committing, so the refresh lands inside that render and is coalesced away about one time in ten (22/22 navigated, 20/22 counted). With the extra frame: **22/22 navigated, 22/22 counted**, median 422 ms, slowest 678 ms. The `.catch` is part of the shape: an unhandled rejection on a page the user has left has nobody to tell.
- The STRANDING is specific to a CONCURRENT push (#529, measured). The 22/22 and 11/11 above are a `<Link>` whose `onClick` fires the action: the push is already in flight when the transition or refresh arrives, so there is something to supersede. A handler that `await`s the action and only THEN pushes has no in-flight push, and both of #308's unswept violations navigated 22/22 with the banned shape still in place. They are still violations — the refresh re-renders a route nobody will be on, which is dead work and one wrong edit away from the concurrent shape — but do not expect a repro from the `await`-then-push form.
- …and the rule is SWEPT, not spot-fixed (#529): `src/components/navigating-clicks.test.ts` is a TABLE of every handler that ends in a `router.push`, asserting each owns no transition and no `router.refresh()`, plus that the actions reached only by a leaving caller carry no server `refresh()` either. A new leaving handler is a new ROW. Two things it caught: `<form action={fn}>` runs `fn` inside a transition REACT owns, so a leaving submit must be wired through `onSubmit` (`TaskForm`); and an action whose ONLY caller leaves should keep `revalidatePath` (it freshens the destination) and drop `refresh()`.
- Legitimate client state is UI state only: pagination cursors, drag-and-drop, open/closed (`PipelineView`).
- A message that a `router.refresh()` accompanies must NOT live inside the subtree that refresh re-renders — the refusal that fires the refresh unmounts its own `<Alert>` mid-read. Raise it through the root `<Toaster>`, a sibling nothing below can unmount, and never delay the refresh for it.
- A `useActionState` PRESS WHOSE ACTION CALLS `refresh()` CAN STRAND, INTERMITTENTLY, AND ONLY WHEN THE BUILD IS COLD (#665, reproduced on Next 16.2.2 — the version #658 shipped on). #658's pre-#662 shape, restored verbatim and pressed 12 times: 3 stranded, all of them the first or second press against a freshly deployed build; 0 of 9 later presses, which commit in 400–1200 ms. The write lands every time — all 12 swapped `users.email` — so what strands is the render. Reversing the account order moved the strand with the POSITION, not the account. **A warm bisect finds nothing**: a 2x2 over `refresh()` and over whether the success render keeps the `<form>` it was submitted from committed in all four cells, which is why #658 went unexplained. This is NOT the stranding in the entries above — those are about a push (#308, #529) and about an alert unmounted by its own refresh; here the press itself never commits.
- …so an outcome a reader DEPENDS ON must not wait on that transition. `confirmEmailChangeAction`'s redirect is kept for this reason and not only for the UX: a server-rendered redirect cannot show the symptom. Still open, and not enough trials to separate: whether the cold first press alone is sufficient, or whether it also needs the success render to drop the submitting `<form>` (`requestEmailChangeAction` keeps its form and has not been seen to strand, n=1 cold). Nothing here licenses removing a row from #529's sweep.

## Settings — the hash-driven modal

Applies to `src/lib/settings/{settings-hash,sections,section-view,section-data}.ts`, `src/components/settings/{settings-modal,settings-link}.tsx`, the section components under `src/components/settings/sections/`, `src/app/api/settings/sections/[section]/route.ts`, and what is left of `src/app/(dashboard)/settings/`.

- ⚖ SETTINGS IS CLIENT STATE ADDRESSED BY A FRAGMENT, never a route (ruled 2026-08-22 for #657, superseding the "real paths, never a hash" half of 2026-08-21 §187; CS-001). `#settings/<section>` over ANY page opens the modal over that page: `/meetings#settings/account`, `/phase#settings/church`. A section switch rewrites the fragment and NOTHING else — no navigation, no RSC render of the screen behind, no remount of the modal, so the open animation plays once however many sections a reader opens. `settings-modal.tsx` reads `location.hash` through `useSyncExternalStore`, whose SERVER snapshot is always "no fragment" because a fragment never reaches a server; that is what makes a cold load render the page normally and open the modal over it on hydration.
- ⚖ `src/lib/settings/settings-hash.ts` OWNS THE WHOLE HISTORY POLICY, and it is the only file that moves history for settings. OPEN pushes exactly ONE entry. A SWITCH replaces, so settings occupies that one entry however far a reader roams. CLOSE goes `back()` when this document pushed an entry ON THIS PAGE, and otherwise strips the fragment IN PLACE — a cold-loaded `/phase#settings/church` closes to `/phase`, still mounted, never reloaded and never bounced to an account's home.
- ⚖ …AND THE PAGE HALF OF THAT LAST RULE IS LOAD-BEARING (#657 review). A latch watching only the FRAGMENT concluded "this document pushed it" for an arrival that changed page and fragment in ONE entry — which `verify-email/confirmed/page.tsx` does, linking to `/dashboard#settings/account` from inside the dashboard group — and Close then walked the reader back to a consumed token screen instead of shutting the modal. The rule is ONE expression, deliberately: it was two lines that agreed with each other until they did not, and the redundant one made a red check of the other prove nothing.
- ⚖ THE POLICY IS DRIVEN BY A TEST, not only located by one. `settings-hash.test.ts` runs the real module against a fake `window` — cold load closes in place, an in-page open closes with one step back, four switches add no entries, a page-and-fragment arrival closes in place, Back closes and Forward reopens, a history-API write is noticed. Every source guard in `settings-mechanism.test.ts` passed while three defects sat in this module; a topological guard cannot see timing. Nothing is dependency-injected: the module reaches `window` when CALLED, which is what makes a fake enough.
- ⚖ A SETTINGS **PATH** IN AN HREF IS A BUG, not a broken link, and that is why it is a test. `/settings/<section>` still resolves — `src/app/(dashboard)/settings/{page,[section]/page}.tsx` permanently redirect it to `/dashboard#settings/<section>` for mail and bookmarks — so a hardcoded path lands the reader on the right section after a FULL PAGE LOAD that discards the screen they were on. Every in-app link goes through `settingsSectionHref` (a bare fragment, for a dashboard screen) or `settingsSectionUrl` (path plus fragment, for mail and the redirects). A server redirect can WRITE a fragment it can never READ, which is the asymmetry the four deleted routes retire on. `settings-mechanism.test.ts` sweeps for the path form; `scripts/prove-settings-hash.ts` re-proves the redirects and that no dashboard response carries a modal.
- ⚖ THE SECTION BODIES ARE `"use client"` AND ARE FED BY ONE ENDPOINT — `GET /api/settings/sections/<id>`, which refuses a sessionless caller with a 401 and otherwise hands `loadSettingsSection` (`@/lib/settings/section-data.ts`) the id. That function asks `settingsSectionsFor` — the SAME registry gate the navigation is built from — and answers with a finished view model (`./section-view.ts`) or `{ ok: false }`, on which the modal falls back to the default section. That fallback is the deleted routes' `redirect()`, moved, and it is a 200 because it is an ANSWER: a stale bookmark or a seat that changed is a reader's ordinary mistake, not a failure. The refusal that MATTERS is still each action's `requireSeat`; this decides what renders. Every date leaves the endpoint as a STRING formatted against `APP_TIME_ZONE` (→ Date & Time Rendering), which JSON forces anyway.
- …and the reason they are client components is MEASURED, not preferred (#657). A server function returning the section's JSX was built and probed on Next 16.2.2 with Turbopack, on a static route and on a `force-dynamic` one: a server function CAN return a server-rendered tree, but a tree containing ANY client component fails to serialize — `Could not find the module "…" in the React Client Manifest` — and every section here is mostly client components. Do not re-propose it without re-running that probe.
- ⚖ RECONCILIATION AFTER A WRITE RIDES `serverRenderId`, a value the dashboard layout regenerates on every server render and the modal takes as a prop. The modal is not part of any route, so `refresh()` — which every settings action calls (→ Client/Server Data Synchronization) — re-renders the layout and therefore changes this prop, and that is the ONLY thing that tells an open section to read itself again. Nothing the modal remembers is in React state: the read's promise and its answer both live in module scope, keyed by the render id, so neither can go stale where a component would have to notice (→ Client/Server Data Synchronization, the stale-while-revalidate exception). Deleting the prop makes every settings write appear not to save until the modal is reopened — and it is also the only invalidation key the cache below has, so deleting it makes that cache permanent.
- ⚖ …AND THE READ IS A ROUTE HANDLER, NEVER A SERVER ACTION, for that exact reason (#657). Every server-ACTION response carries a fresh RSC render of the current route — that is how `refresh()` delivers an update — so a read spelled as an action regenerates `serverRenderId` with its OWN answer and asks for itself again, without end. The two spellings are indistinguishable in a diff, which is why `settings-mechanism.test.ts` asserts the read module carries no `"use server"` and that the modal reaches it by `fetch` rather than by import.
- ⚖ THE READ IS CACHED IN MODULE SCOPE, keyed by section, `serverRenderId` and the retry count, and a `useMemo` CANNOT hold it (#657, measured). The section is unwrapped with `use()`, so the promise must exist before the render that consumes it — and a render that suspends is DISCARDED AND REPLAYED, a replay re-runs `useMemo`, a re-run mints a second promise, and consuming that one suspends again. On the preview that was a loop at about six reads a second for as long as the modal stayed open. Module scope is not React's to drop. It is safe there for the same reason `openedByPush` is: nothing renders the dialog on the server, because the store's server snapshot is always "no fragment".
- …and it holds THREE READS PER SECTION, keeps the ANSWER beside each promise, and drops the FAILURES ALONE when the modal closes (#673, superseding #657's "two keys, dies with the visit"). At least two per section because React can render two keys in one window — a `refresh()` transition at the new id while a keystroke re-renders the committed tree at the old one — and a single slot has each evicting the other, which is the same loop at a lower rate; PER SECTION because all five are prefetched together, so a global cap of two had the modal evicting its own prefetch as it filled it. The answer is kept beside the promise because a promise has no synchronous value and a second map of views would be a second place to decide "the newest answer for this section" — `cachedSectionView` is one scan over one insertion-ordered map, so the newest READ wins rather than the newest RESPONSE and a straggling earlier read cannot overwrite the value a reader just saved. #657 dropped the whole read on close to avoid serving "the previous visit's roster"; that roster is now served ON PURPOSE, because `serverRenderId` says when it stopped being true. FAILURES ARE THE EXCEPTION and must not survive: `attempt` is the dialog's own state and resets to 0 on unmount, so a kept failure is replayed under the very key the reader arrives back on and the section looks broken for the life of the tab.
- …and the close asks "IS THIS AN ANSWER", never "did this fail" (#673 review). A read still IN FLIGHT at close has failed at nothing yet, so the second question keeps it — and it writes its failure into the map afterwards, under attempt 0, at a render id that has not moved, which is the exact key the next opening lands on. The prefetch makes that five wide: opening starts five reads and closing a second later can leave all five in flight, so sections the reader never looked at come back broken. Dropping in-flight reads there is safe because the dialog has unmounted and nothing is suspended on them.
- ⚖ THE RETRY COUNT IS PER SECTION, not per dialog (#673 review). It is a segment of a per-section read key, so as one number for the whole modal a Try again in ANY section moved every other section's key to `attempt: 1` — which nothing had prefetched — and every switch for the rest of the visit paid a fresh read. The error path silently undoing the feature is the failure mode to look for whenever dialog-wide state is spliced into a per-section key.
- ⚖ THE STALE COPY IS `inert` AND `aria-hidden` (#673 review). A Suspense fallback is a SECOND TREE — React carries no state from it into the children, so the instance is unmounted and replaced the moment the read lands. The sections are forms, so an interactive stale copy hands the reader a password field or an optimistic toggle that a revalidation a few hundred milliseconds later throws away with whatever they typed into it. `inert` costs nothing the skeleton did not already cost, since this is the moment that used to BE a skeleton, and it also settles the duplicate-`id` question: a re-suspended boundary keeps its children mounted and hidden beside the fallback, and only one of the two may answer to a label. The right end state is ONE tree — the settled answer read through the store the fragment already uses, with no fallback — which is a larger change than #673 and is written down rather than half-done.
- ⚖ EVERY VISIBLE SECTION IS PREFETCHED ON OPEN, ONCE PER OPENING, AND NEVER IN A BURST AFTER A WRITE (#673). The dialog warms `visibleIds` — at most five, each small — from an effect that runs on mount, which is why a section switch costs no request. It must NOT be spelled during render: that fires five reads on every `serverRenderId` change, so one notification toggle would re-read four sections nobody is looking at. After a write the section ON SCREEN refetches (that is `serverRenderId` doing its existing job) and the other four revalidate lazily, when they are next viewed. The prefetch walks `visibleIds` and nothing else, which is what keeps a gated section out of the cache. `readTeam` still calls `expireLapsedUserInvitations`, so that idempotent, tenancy-scoped sweep now runs on every settings OPEN for an account that can see Team, rather than on every Team view.
- ⚖ THE SUSPENSE FALLBACK IS THE CACHED SECTION, NOT THE SKELETON, whenever this tab holds one (#673) — that is the whole of stale-while-revalidate, in one expression, with no store subscription and no second render path: the boundary is keyed by SECTION, the cached values paint the moment it suspends, and `use(request)` replaces them with the fresh ones. The key MUST NOT gain `serverRenderId`: that makes every write a new boundary, and a new boundary drops what the reader is looking at. The skeleton survives for a section this tab has never loaded, and a failure still reaches the pane because the fallback is only ever on screen while the read is pending.
- ⚖ THE THREE READ FAILURES ARE TOLD APART, and collapsing them had a silent worst case (#657 review). `refused` is the SERVER's answer and corrects the fragment to the default section; `unauthorized` (a 401) sends the reader to `loginPathFor`, which is what the rest of the product does with a stale session; `failed` names the failure and offers a Retry that bumps the read key, so it is a fresh request rather than a replay of the cached one. As one value, an expired session read as a refusal, bounced to a default section whose read had already failed and was cached, and drew a skeleton that never resolved.
- ⚖ THE MODAL OPENS THROUGH `pushState`, NEVER A NATIVE FRAGMENT NAVIGATION (#657, measured). Next's client router does not observe a native `#`-navigation, so its copy of the URL keeps saying `/dashboard` — and the first `refresh()` afterwards rewrites the address bar from that copy and takes the fragment with it, closing the modal under the reader's hands on their first save. `pushState` is the documented way to hand the App Router a URL it did not navigate to. Every in-app settings link is therefore `<SettingsLink>`, which is the real `href` (copyable, middle-clickable, enough with JavaScript off) AND the cancelled plain click together; `settings-mechanism.test.ts` fails on a bare `href={settingsSectionHref(…)}` anywhere else. It takes `ComponentPropsWithRef<"a">` and SPREADS them, which is not politeness: its first caller is `<DropdownMenuItem asChild>`, and Radix composes by cloning the child with the item's `ref`, `role="menuitem"` and roving-focus wiring — a component taking three named props dropped all of it and the avatar menu quietly stopped being a menu. `settingsSectionUrl` — path AND fragment — stays allowed in an href, because that is a real navigation the router performs and therefore knows the fragment of. #670 was filed against this rule and retracted: the repro reached the modal by typing `/dashboard#settings/account`, the unsupported path this rule names, and so reproduced a bug #657 had already fixed. Reach a surface the way the product reaches it before believing a repro.
- ⚖ THE MODAL IS MOUNTED ONCE, UNCONDITIONALLY, BY THE DASHBOARD LAYOUT, and draws nothing until the fragment names a section. A second mount is #646's two dialogs, two focus traps and two Close buttons with a different cause; `settings-mechanism.test.ts` forbids one. The `@settings` slot, its five route files, `(dashboard)/default.tsx`, `settings-surface.tsx` and `settings-slot.test.ts` are all DELETED — there is no interception, no parallel slot and no `intercepted` prop left to reason about.

## Design Tokens — Contrast

The guards are four suites under `src/app/`: `theme-tokens.test.ts`, `text-contrast.test.ts`, `focus-ring.test.ts`, `status-badge-scale.test.ts`.

Applies to `src/app/globals.css` and every stylesheet under `src/app/`; colour maths comes from `src/lib/testing/theme-color.ts`.

- ⚖ WCAG AA (4.5:1) is the standard that BINDS `--muted-foreground`; APCA is advisory and never a reason to lighten it — the token sits at APCA Lc 68.2 on `--muted` and ships anyway.
- ⚖ The cost of darkening `--muted-foreground` is INLINE-LINK SEPARATION, and it is paid in CSS, never by capping the token's lightness: `p a[href]` carries a permanent underline at REST. Never delete that rule and never put `no-underline` on a link inside prose.
- The diagnostic for a LOST underline — an unlayered declaration beating the `@layer base` rule — is an asymmetry in computed style: `text-underline-offset: 4px` present while `text-decoration-line` is `none`. Only the browser or the stylesheet guard sees it.
- ⚖ `--destructive` is DESIGN.md's ruled `danger` #B4432F, NOT a red chosen to clear 4.5:1 — the app shares the palette. If danger has to move, it moves in DESIGN.md FIRST and `globals.css` follows.
- Accepted residual (DECISION): `bg-destructive/10 text-destructive` — twelve call sites — measures 4.07:1 light and 3.89:1 at `dark:bg-destructive/20`. NO token value fixes it; the remedy is a solid ground or a text-on-tint role token.
- ⚖ The person-status badges are the TINTED EDITORIAL scale: each status that carries colour paints ONE hue three ways in `people/status-colors.ts` — pale ground, deep ink, hairline border — mirrored in dark, so every entry spells six classes. `prospect` stays NEUTRAL; `attendee`/`launch_team` share ONE hue at different TINT LEVELS. All fourteen pairs must clear AA and there is NO deferral list.

## Requirement Ids

The guard is `ops/tests/requirement-ids.test.mjs`. Applies to every requirement id cited in `src/` or `memory/`, and to the FRD tables under `product-docs/features/*/frd.md`.

- Every requirement id cited in `src/` or `memory/` RESOLVES to an FRD row, and the test fails a PR that mints one that does not. When code cites a slice id (`OV-007a`, `VM-016c`) no FRD row defines, the ROW comes to the FRD — never rename the citation onto a neighbouring row unless it truly means the same requirement, and never write a row for an id nothing cites.
- `product-docs/` and `memory/` are carved OUT of the docs-only shortcut in `pull-request-checks.yml` because that test reads both. Removing the carve-out disarms the guard against the change it most needs to catch: the markdown-only FRD edit that drops a row something still cites.
- `AES-256` and `SHA-256` match the id pattern and are NOT requirement ids; the test's `NON_IDS` excludes them, and a prefix is added there only once it actually appears.
